# 知识中心体系化评估与优化建议（PMWB · 系统级重审）

> 目的：站在整个 PMWB 系统角度，评估知识中心四个子模块（知识库 / 产品圣经 / 知识沉淀 / 按领域浏览）当前「内容设计与业务知识底层定义割裂」的问题，给出体系化重构方案与分阶段路线。
> 基线代码：`frontend/src/views/{KnowledgeView,ProductBibleView,OperationNotesView,DomainKnowledgeView}.vue`、`backend/routers/{knowledge,product_bible}.py`、`backend/core/config.py`、`pmwb_business_domain` / `pmwb_knowledge_item` / `pmwb_knowledge_link`。

---

## 0. 一句话结论

知识中心目前是「四个各说各话的入口」，根因是**底层同时存在四套互不买账的业务知识定义**（领域表 / 知识分类 / 硬编码产品圣经配置 / Obsidian 目录），导致「主笔记」被定义了两遍、知识沉淀被错配成又一个文件夹浏览器、产品圣经游离在领域模型之外。优化方向只有一条：**以 `pmwb_business_domain` 为唯一主轴，把 `pmwb_knowledge_item` 当节点、`pmwb_knowledge_link` 当边，构建一张领域驱动的知识图谱；四个子模块全部降维为这张图的四种视图。**

---

## 1. 我锚定的「知识中心关键能力要求」

你此前对知识中心建设提过的关键能力（来自《需求规格说明书》模块6/7 + Obsidian 归档方案 + 2026-08-05 双向联动方向 + kc-2 落地规范），我据此评估。如还有未覆盖的口头要求，请补给我：

1. **单一事实源**：Obsidian 为权威存储，PMWB 只做索引与联动，不另起炉灶。
2. **按业务领域聚合**：以二级业务领域为顶层维度，把工作流与知识「聚」在一起（你的原话：*按业务领域聚合工作流 + 知识自动沉淀回流*）。
3. **知识自动沉淀回流**：需求 / 工单 / 会议 / 重点工作等过程资产，能自动沉淀为知识并回流到对应领域。
4. **双向联动**：业务对象 ↔ 知识笔记可互查、互链。
5. **产品圣经 = 产品档案 / 运维知识**：可读、可在线编辑、写回 Obsidian。
6. **层级化主笔记体系**：每个领域一个主笔记 + 子笔记分组（kc-2 设计案 v2.0 要求）。

## 2. 现状盘点：四个子模块各自为政

| 子模块 | 实际底层 | 入口逻辑 | 与领域模型的关联 |
| :--- | :--- | :--- | :--- |
| **知识库** (`KnowledgeView`) | `pmwb_knowledge_item` | 按 **Obsidian 文件夹树** + 分类 + 标签筛选 | ❌ 完全不露 `domain_code`，与领域脱钩 |
| **产品圣经** (`ProductBibleView`) | `core/config.py:PRODUCT_BIBLE`（硬编码 2 条） | 按配置业务切换器读取 Obsidian 文件 | ❌ 不读 `pmwb_business_domain`，与领域表零关联 |
| **知识沉淀** (`OperationNotesView`，路由 `/knowledge-center/notes`) | 直接扫 `11-业务运营` / `01-业务知识` 文件夹 | 文件夹浏览器 + 「关联到工单」 | ⚠️ 名为沉淀实为又一个文件夹浏览器，与「经验沉淀入口」设计意图不符 |
| **按领域浏览** (`DomainKnowledgeView`) | `pmwb_business_domain` + `get_related` 聚合 | 领域卡片 → 主笔记 + 子笔记 + 需求/会议/工单/时间线 | ✅ 唯一真正以领域为轴的入口 |
| （附）**SQL脚本库** (`SqlScriptView`) | `pmwb_sql_script` | 独立表、独立范式 | ❌ 无任何 `domain_code`、无知识图谱关联，仅是「挂在知识中心名下」 |

**关键矛盾证据**
- `PRODUCT_BIBLE` 仅 2 条（`group-sms` 集团短信、`e-contract` 电子协议），而领域表有 12 个二级领域种子——产品圣经覆盖与领域体系完全不对齐，且新增业务要改代码配置而非建领域。
- 「主笔记」被定义了两遍：① `产品圣经` 配置里的「产品档案」；② `knowledge_item.note_type='main'` 的「业务知识主笔记」。二者是同一概念（某业务的总入口笔记）却两套实现。
- 「知识沉淀」标签指向的 `OperationNotesView` 文案写的是「运营关联的知识笔记」，与规格书「随手笔记与经验沉淀入口」南辕北辙。

## 3. 根因诊断：四套底层定义互相不买账

```
        ┌─────────────────┐
   ①   │ pmwb_business_  │  领域轴（按领域浏览用）
        │ domain (12 种子) │
        └─────────────────┘
                 │  ← 与 ② 无强制映射
        ┌─────────────────┐
   ②   │ knowledge_item.  │  内容分类轴（知识库用）
        │ category(product/│  product/operation/...
        │ operation/...)   │  与 domain_code 是平行两轴
        └─────────────────┘
                 │  ← 与 ③ 完全独立
        ┌─────────────────┐
   ③   │ PRODUCT_BIBLE    │  硬编码配置（产品圣经用）
        │ 配置 2 条        │  不读领域表
        └─────────────────┘
                 │  ← 与 ④ 各写各的
        ┌─────────────────┐
   ④   │ Obsidian 目录     │  01-业务知识/{领域}/
        │ 11-业务运营/...   │  kc-3 已收敛但 UI 仍按目录浏览
        └─────────────────┘
```

1. **① 与 ② 是平行两轴**：一条知识既有 `category`（内容类型）又有 `domain_code`（归属领域），但二者无约束映射（如 `category='product'` 不指向任何具体领域），系统无法回答「这个领域下有哪些产品知识」。
2. **③ 游离于 ① 之外**：产品圣经靠手写配置，不消费领域表，导致「产品圣经」和「领域主笔记」是同一事物的两个孤儿实现。
3. **④ 仍被当 UI 维度**：知识库/知识沉淀按 Obsidian 目录树浏览，等于把存储结构当产品导航，领域维度被埋没。

## 5. 目标架构：一个底层 + 四种视图

### 5.1 统一底层（唯一事实源）

- **唯一主轴** = `pmwb_business_domain`（二级领域）。
- **节点** = `pmwb_knowledge_item`，字段语义重定：
  - `domain_code`：**必填**，归属领域（FK）。
  - `note_type` ∈ `main / sub / sediment / manual`（主笔记 / 子笔记 / 流程沉淀 / 手动）。
  - `content_type`：沿用现 `category` 取值（product/operation/requirement/meeting/personal/study），**降级为筛选 facet，不再是分组轴**。
  - `source_type` / `obsidian_path` 保留。
- **边** = `pmwb_knowledge_link`（知识 ↔ 需求/工单/会议/重点工作/交付物）。
- **Obsidian 目录** = 纯存储实现（`01-业务知识/{领域}/...`），不再作为 UI 导航维度。

### 5.2 产品圣经去配置化（消除双重主笔记）

- 废弃 `PRODUCT_BIBLE` 硬编码配置。
- 「产品圣经」= 某领域的 **主笔记（`note_type='main'`）**，由 `product-bible` 路由按 `domain_code` 解析并读取其 Obsidian 文件；docx 特例（如电子协议白皮书）作为该领域主笔记的 `archive_format` 属性保留渲染链路。
- 前端 `ProductBibleView` 改为用 `BusinessDomainSelect` 选领域，复用与知识库/沉淀同一套 Markdown 渲染与写回组件。

### 5.3 信息架构重排（四视图统一到一张图）

| 新标签 | 本质 | 底层读法 |
| :--- | :--- | :--- |
| **领域全景**（原按领域浏览） | 图谱 HUB | 领域卡片 → 主笔记 + 子笔记 + 关联需求/工单/会议/时间线 |
| **知识检索**（原知识库） | 全局搜索/筛选视图 | 全部 `knowledge_item`，按 `domain_code` + `content_type` + `tag` 三维筛选（砍掉文件夹树） |
| **产品圣经** | 领域主笔记阅读/编辑视图 | 选领域 → 渲染该领域 `note_type='main'` 笔记 |
| **沉淀与速记**（原知识沉淀） | 录入 + 收件箱视图 | ① 速记入口（随手写一条到某领域/个人知识）② 沉淀收件箱（已 sediment 未 link、未归领域的笔记）③ 关联快捷操作 |
| （移出）**SQL脚本库** | 工具，非业务知识 | 迁至「工具/资源」，可选带 `domain_code` 标记，不与知识图谱混为一谈 |

### 5.4 闭环验证

工作流对象（需求/工单/会议）→ kc-2 已实现的 `sediment_*` 沉淀进领域主笔记的「场景规则」子笔记 → 该主笔记即「产品圣经」→ 「领域全景」与「产品圣经」从同一底层读出。**打通后，产品圣经不再依赖任何硬编码配置，沉淀回路也真正闭合。**

## 6. 分阶段优化路线图（对齐 DEV_WORKFLOW 分级）

| 阶段 | 分级 | 范围 | 验收 |
| :--- | :--- | :--- | :--- |
| **P0 统一底层定义** | S1（需方案门禁） | 明确 `domain_code` 必填 + `content_type` 取代 `category` 语义 + 「领域主笔记即产品圣经」映射规则；废弃 `PRODUCT_BIBLE` 配置 | 出方案文档与老大确认；数据模型无歧义 |
| **P1 产品圣经去配置化** | S2 | `product-bible` 路由改按 `domain_code` 解析主笔记；`ProductBibleView` 改 `BusinessDomainSelect`；保留 docx 渲染 | 产品圣经随领域表增减，不再改代码 |
| **P2 知识库→知识检索** | S2 | 去掉文件夹树，改 `domain + content_type + tag` 三维筛选；统一卡片组件 | 知识库与领域全景共享同一 `knowledge_item` 数据源 |
| **P3 知识沉淀正名** | S2 | 实现速记入口 + 沉淀收件箱 + 关联快捷；退役 `OperationNotesView` 的错配浏览器 | 「知识沉淀」确有速记与收件箱，而非又一个文件夹浏览器 |
| **P4 收口** | S3 | SQL脚本库移出/归并；全局去重重叠入口；主笔记空态保护 | 四视图共享同一底层，无重复定义 |

**完成标准（Done）**：四个子模块共享同一 `domain + knowledge_item + link` 模型；任意知识可在「领域全景 / 知识检索 / 产品圣经」三处从同一底层读出；产品圣经不再依赖硬编码配置；知识沉淀确有「速记 + 收件箱」能力。

## 7. 风险与对策

- **存量产品圣经仅 2 条**：迁移量小；docx 源（电子协议白皮书）保留 `archive_format` 渲染路径，避免功能回退。
- **去文件夹树可能影响习惯**：保留一个「按 Vault 目录」折叠高级视图，但默认导航维度改为领域。
- **领域主笔记空态**：打开产品圣经前先 `ensure-main-notes` 保活，空则提示「生成主笔记」。
