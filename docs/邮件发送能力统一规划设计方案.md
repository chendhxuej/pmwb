# 邮件发送能力统一规划设计方案

> 范围：PMWB（个人工作台系统）中所有"邮件发送 / 邮件预览"场景的统一治理
> 目标：把分散在各页面的邮件能力，收敛为「统一模板 + 统一预览 + 统一签名 + 统一部署」的一层能力
> 依据：已实地核查 `统一邮件中心`(localhost:3210) 接入指南、`backend/services/mail_dispatch.py`、`frontend/src` 各页面实现

---

## 一、现状分析

### 1.1 已具备的统一基础（这是资产，要保留）

- **发送通道已统一**：所有发信实际都经 PMWB 后端门面 `backend/services/mail_dispatch.py` 的 `dispatch_email` → 统一邮件中心 `localhost:3210/api/send`。前端没有直连 SMTP，通道层面已经收敛。✅
- **模板能力已具备**：统一邮件中心提供模板 CRUD 与 `POST /api/templates/:id/render`，并建议 `type` 命名规范（`{项目}_{业务}`）。
- **后端已有预览与签名雏形**：`routers/mail_dispatch.py` 已有 `preview_email` 接口；`mail_dispatch` 用场景注册表声明 `body_format / email_type / add_signature`，并经 `markdown_to_email_html` 注入签名后落库发信。
- **后端已有场景门面**：`meeting.py` 已调用 `dispatch_email`；但 **`reminder` / `plugin` / `work_report` / `task_center` / `supervise` 仍绕过门面直接调用 `EmailCenterClient`**，导致统一签名、HTML 内联样式、EmailRecord 落库仅在会议场景生效。

> 结论：**发送层并未完全统一，约半数场景绕过了门面；问题同时出在"后端 bypass + 前端预览分裂 + 模板/签名无治理 + 缺共享组件"**。需要先把绕过门面的发信收口，再统一前端预览与签名治理。

### 1.2 核心问题（痛点 → 根因）

| 痛点 | 根因 |
|------|------|
| 各场景邮件预览很乱、样式/能力不一 | 预览是各前端页面**自己实现**的，后端无统一预览约束；共 4 套预览实现 |
| 个别场景功能有问题 | `WorkReportView` 预览是纯前端 Markdown（无签名/无 HTML 包装），实发走后端门面加签名 → **预览 ≠ 实发**；另有 loading 失效、覆盖用户编辑等 bug |
| 模板各自维护、无统筹 | 模板虽有 `type` 概念，但**无"场景→模板"的显性注册表与变量契约**，前端传参 (`mail_type`/`send_type`/`operator`/无) 不统一 |
| 公共签名无从统一配置 | 签名散在 `markdown_to_email_html` + 场景注册表，且前端还硬编码 `add_signature:true`，**没有"签名管理"入口**，改签名要动代码 |

### 1.3 现状能力盘点

| 层面 | 现状 | 评价 |
|------|------|------|
| 发送通道 | `meeting` 经 `mail_dispatch` → 3210；`reminder/plugin/work_report/task_center/supervise` 绕过门面直发 3210 | ⚠️ 通道半统一，需收口 |
| 模板 | 3210 模板库 + render，但无治理 | ⚠️ 有基础、缺治理 |
| 预览 | 4 套实现（mail-dispatch / task-center dry_run / 纯前端 / 无） | ❌ 分裂 |
| 签名 | 后端场景注册表控制 + 前端硬编码冲突；绕过门面的场景无签名 | ❌ 未统一 |
| 共享组件 | `MailComposeDialog` 仅会议页用，其余自写 | ❌ 名存实亡 |

### 1.4 不一致与缺陷清单（含严重度，来自代码探查）

- **【高】** `WorkReportView.vue` 预览为纯前端 `MarkdownRender`（无签名/无 HTML 包装），实发经后端门面加签名 → 预览与实发内容不一致。
- **【高】** 发信/预览共 4 套实现，能力差异大（有/无预览、本地/后端），无统一入口。
- **【中】** `MailComposeDialog` 发送按钮 `:loading` 用了组件内 `sending`（永为 false，父组件管 `sendingMail`）→ 无 loading 态，可能重复发送。
- **【中】** `MeetingView` 硬编码 `add_signature:true` 且 `body_format:'html'`（传的却是 Markdown）；发送签名由后端场景注册表决定，前后可能不一致。
- **【中】** `TaskCenterView.handleTaskEmailSend` 未校验 `body` 非空，dry_run 预览会覆盖用户手动编辑。
- **【低】** `RequirementView`/`Reminder` 完全无邮件预览；`type` 字段不统一（`mail_type`/`send_type`/`operator`/无）。

## 二、设计原则与目标

**设计原则**
1. **单一事实源（SSOT）**：场景 → 模板 → 签名 → 预览格式，全部由后端场景注册表决定；前端只传 `scene` + 变量/内容。
2. **预览即实发**：预览必须复用 `dispatch_email` 的同一格式化链路（`preview_email` 应作为**唯一**预览入口），杜绝预览/实发漂移。
3. **能力下沉**：把"模板选择、签名注入、收件人解析、loading/失败/防重"抽到共享前端组件 + 后端门面。
4. **配置化运营**：模板与签名可后台配置，不硬编码；变量有 schema 校验。

**目标**
- 所有邮件页面的预览与实发内容 **100% 一致**；
- 新增邮件场景接入 **≤ 0.5 人日**（只登记 scene + 变量）；
- 签名/模板变更 **零代码**（后台改）；
- 发送有 loading、有失败重试与提示、无重复点击。

## 三、总体架构（统一邮件能力层）

```
PMWB 各页面（会议/任务/周报/需求/催办）
        │  只传：scene + to/cc + variables | rawContent
        ▼
┌─────────────────────────────────────────────┐
│  共享前端组件  MailComposeDialog（全站唯一）   │
│  - 收件人解析  - loading/失败/防重  - 预览    │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│  后端门面  services/mail_dispatch.py          │
│  - 场景注册表(scene→template/type/signature)  │
│  - 变量校验  - markdown_to_email_html(含签名) │
│  - preview_email（预览） / dispatch_email（发）│
│     ↑ 两者共用同一格式化函数（预览即实发）     │
└─────────────────────────────────────────────┘
        │
        ▼
   统一邮件中心 localhost:3210  (/api/send, /api/templates)
        │
        ▼
    SMTP 出信 + 日志（按 email_type/scene 可统计）
```

## 四、分模块设计方案

### 4.1 定制化邮件模板治理体系

- **显性化"场景注册表"**：把 `mail_dispatch` 里散落的 `body_format/email_type/add_signature` 抽成一张可配置注册表（建议落库或配置文件），每条记录：
  `scene | email_type | template_key(指向3210模板或内置) | body_format | signature_key | 变量schema | 默认收件人规则`。
- **模板分层**：
  - ① **系统内置模板**（结构/合规/签名固定的）：代码随版管理，保证兜底；
  - ② **运营可配置模板**（3210 模板库，按 `type` 管理）：文案细节可由运营改，不碰代码。
- **命名与归属规范**：`{project}_{module}_{action}`（如 `pmwb_meeting_notice`、`pmwb_workreport_weekly`），与 3210 `type` 对齐；建立《场景-模板映射清单》文档（见第八章）。
- **变量契约**：每个 scene 声明变量 schema（名称 / 类型 / 必填），render 前校验，从根上消灭"渲染为空"类问题（对应接入指南 Q2）。

### 4.2 统一邮件预览能力

- **收口到后端 `POST /mail-dispatch/preview`**：入参 `{scene, to, cc, variables | rawContent}`，返回与 `dispatch_email` **完全相同**的 HTML（含签名/格式）。
- **前端统一封装**：新增 `useMailPreview` hook + 升级 `MailComposeDialog` 为**全站唯一**发件/预览组件，替代现有 4 套；入参统一为 `{scene, to, cc, variables|rawContent}`。
- **预览 = 实发**：解决 `WorkReportView` 不一致；预览区展示：主题 / 收件人 / 正文(渲染后 HTML) / 签名 / 附件占位。
- **防覆盖**：预览是只读渲染，用户编辑发生在"变量层"，不在渲染后的 body 上改（解决 TaskCenter 覆盖 bug）。
- **校验前置**：`body` 非空、收件人有效、变量齐全——`preview` 与 `send` 共用同一校验函数。

### 4.3 公共签名统一管理

- **抽离为独立签名配置**（在 3210 或 PMWB 后台增加签名管理）：支持多签名档（如"产品团队通用""会议专用"），每条含 名称 / HTML 内容 / 适用范围 / 是否默认 / 变量（如 `{sender_name}`、`{team}`）。
- **由后端按 scene 解析应注入的签名档**并统一注入；**前端禁止再传 `add_signature`**，消除 `MeetingView` 硬编码冲突。
- **渲染时替换签名变量**，保持与正文同一格式化链路。

### 4.4 统一部署与接入规范

- **新页面接入只需 3 步**：① 在场景注册表登记 `scene` + 变量 schema；② 选用/新建模板（3210 或内置）；③ 前端只调共享 `MailComposeDialog` + 后端 `dispatch_email`。
- **共享组件落地**：`MailComposeDialog` 升级为全站唯一发件/预览组件，统一处理收件人解析、loading、失败重试、防重复点击（修掉当前 loading 失效 bug）。
- **可观测**：所有发信带统一 `email_type` + `scene`，日志可经 3210 `/api/logs` 按项目/模块统计。
- **灰度与回归**：每个 scene 配一条"黄金样例"（输入 → 预期渲染 HTML），纳入冒烟测试，防止预览/实发漂移。

## 六、验收标准

- [ ] 所有邮件页面：预览内容 与 实发内容 diff 一致（自动化校验）；
- [ ] 新增邮件场景接入 ≤ 0.5 人日（只登记 scene + 变量）；
- [ ] 签名/模板变更零代码（后台改即生效）；
- [ ] 发送有 loading、失败重试与提示、无重复点击；
- [ ] `type`/`scene` 字段全站统一。

---

## 七、风险与缓解

- **历史页面改造成本**（任务/需求/周报页需迁到共享组件）→ 分期推进，P0 先止血、P1 再收口，不一次性大改。
- **场景注册表若仍硬编码，治理不彻底** → 必须配置化（P1），否则回到老路。
- **签名多档带来的复杂度** → P1 先支持单一默认签名 + 按 scene 绑定，P3 再扩展多档。
