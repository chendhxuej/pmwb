# 邮件正文宽度统一优化方案

> 评估日期：2026-08-31 ｜ 范围：PMWB 全部发邮件场景 ｜ 目标：所有邮件正文 90% 屏宽居中、基本全屏铺开
> 状态：**已部分实施 —— 会议通知 / 会议纪要已按本方案完成并推送（commit 9cd929f，运行态验证通过）；其余 3210 场景 + 默认 Markdown 场景待全量执行（T1–T6）**

---

## 一、背景与目标

周报邮件正文宽度问题已修复（幽灵单元格 90% 居中）。老大反馈：**项目其他场景发的邮件也存在正文太窄**。

本次目标：把"周报已验证可用"的 90% 居中方案，**统一推广到所有发邮件场景**，不留第二种宽度写法。

验收目标（与周报一致）：
- 邮件正文在屏幕中**居中**展示，占屏宽 **80%~90%**，基本全屏铺开；
- 对任意主流客户端（Outlook Windows / Foxmail / 手机邮箱 / Gmail Web）均稳定生效，不偏左、不溢出。

---

## 二、现状盘点：4 条渲染路径 + 宽度控制矩阵

所有发信触点都收口在 `services/mail_dispatch.dispatch_email` → `_render_mail()`，内部按场景走 4 条渲染路径（`backend/services/mail_dispatch.py` 第 179–250 行）：

| # | 渲染路径 | 命中场景（scene） | 外层框宽度 | 内层正文宽度 | 当前是否"窄" |
|---|----------|-------------------|-----------|--------------|--------------|
| 1 | `render_work_report_html` | `work_report` | 幽灵单元格 90% ✅（已修） | — | 否（已解决） |
| 2 | 3210 模板（`_render_templated`） | `meeting_notice` `meeting_minutes` `action_dispatch` `action_supervise` `task_reminder` `requirement_reminder` `task_center_notify` `task_center_urge` `supervise_sync` `supervise_urge`（共 10 个） | **3210 模板 frame `max-width:600px;margin:0 auto` ❌** | `markdown_to_email_html` 产出 `max-width:680px` ❌ | **是（内外双层叠加最窄）** |
| 3 | 默认 Markdown（`markdown_to_email_html`） | `active_optimization_urge` `active_optimization_sync` `keywork_feedback`（及无模板场景兜底） | 无（裸 div） | `max-width:680px;margin:0 auto` ❌ | **是** |
| 4 | 外部 HTML 透传（`html_passthrough`） | `plugin`（插件类邮件） | 由插件自带 HTML 决定 | 由插件自带 HTML 决定 | 不可控（外部作者定） |

### 关键证据（实测）
- **3210 模板 frame（实测 localhost:3210 接口返回）**：
  ```html
  <div style="font-family:sans-serif;max-width:600px;margin:0 auto;">
    <h2>会议通知</h2> ...静态字段...
    <div>{{{body}}}</div>   <!-- body 由 PMWB 用 markdown_to_email_html 渲染后注入 -->
  </div>
  ```
- **`markdown_to_email_html`（backend/utils/markdown_mail.py 第 587–592 行）**：
  ```python
  _body_wrap = ('font-family:...;font-size:14px;line-height:1.75;color:#1f2329;'
                'word-break:break-word;max-width:680px;margin:0 auto;padding:0 16px;')
  styled = f'<div style="{_body_wrap}">{body_html}</div>'
  ```
- **周报已修复写法（同文件第 290–296 行）**：外层 `width="100%"` table + 左右各 5% 幽灵单元格 + 中间 `width="90%" align="center"` 内容区。

> **排除项**：`services/requirement_stage.py` 的 `max-width:900px` 是 **DOCX 在线预览页**样式，不走邮件通道，与邮件宽度无关，不纳入本次。

## 三、根因

"窄 + 偏左"两处同源：

1. **`max-width:Npx` 在邮件客户端不可靠**：Outlook(Word 引擎) 直接忽略 `max-width`，导致 div 撑满父容器且 `margin:0 auto` 不居中 → 偏左；Foxmail/Web 端虽识别但固定为 600~680px 窄列。这是周报旧写法踩过的同一坑。
2. **3210 模板 frame 也用了 `max-width:600px`**：10 个模板场景是"外层 600px 框 + 内层 680px 正文"双层叠加，所以比周报旧写法更窄。
3. **路径 3 默认 Markdown 场景**裸用 `max-width:680px`，同样偏窄。

> 注：bleach 白名单 `_ALLOWED_CSS_PROPERTIES` 含 `max-width`（第 123 行），所以 `max-width` 不会被净化剥离——它"存活但客户端不支持"，这正是隐蔽性来源（渲染态有、发出去表现差）。

## 四、统一方案（核心：抽一个复用方法，全路径一个写法）

### 4.1 新增复用方法 `_wrap_content_responsive`
在 `utils/markdown_mail.py` 抽取周报已验证的幽灵单元格法为公共方法，全项目只用这一处：

```python
def _wrap_content_responsive(inner_html: str, *, accent: str | None = None) -> str:
    """正文包裹为全屏 90% 居中（幽灵单元格法）。
    外层 width=100% table，左右各 5% 幽灵单元格 + 中间 width=90% align=center 内容区；
    不依赖 max-width/margin:0 auto，Foxmail/Outlook/手机端均绝对居中。"""
    band = (f'<table width="100%" cellpadding="0" cellspacing="0" border="0">'
            f'<tr><td style="height:4px;background:{accent};font-size:0;line-height:0;">&nbsp;</td></tr></table>'
            ) if accent else ""
    return f'''<table width="100%" cellpadding="0" cellspacing="0" border="0" style="margin:0;padding:0;background:#ffffff;">
<tr>
<td width="5%" style="font-size:0;line-height:0;background:#ffffff;">&nbsp;</td>
<td width="90%" align="center" style="padding:20px 0;background:#ffffff;">
<table width="100%" align="center" cellpadding="0" cellspacing="0" border="0" style="background:#ffffff;">
{band}{inner_html}
</table>
</td>
<td width="5%" style="font-size:0;line-height:0;background:#ffffff;">&nbsp;</td>
</tr></table>'''
```

### 4.2 四类路径分别怎么改

| 路径 | 改法 | 落点文件 |
|------|------|----------|
| **1 work_report** | 复用 `_wrap_content_responsive`（去掉 `_render_scheme_a/_b` 内重复幽灵单元格代码，DRY）；签名注入挪进内容列内 | `utils/markdown_mail.py` |
| **2 3210 模板（内层）** | `_render_templated` 调 `markdown_to_email_html(body, wrap=False)`（内层不再自加宽度），宽度交给 3210 frame 单一控制 | `services/mail_dispatch.py` 第 162 行 |
| **2 3210 模板（外层 frame）** | 通过 3210 模板更新 API 批量把 10 个模板 frame 的 `max-width:600px;margin:0 auto` 改为 `_wrap_content_responsive` 同款 90% 幽灵单元格（或至少去掉 max-width 改 `width:100%`） | 3210 服务端（localhost:3210） |
| **3 默认 Markdown** | `markdown_to_email_html` 改用 `_wrap_content_responsive` 包裹（去掉 680px div） | `utils/markdown_mail.py` 第 587–592 行 |
| **4 插件透传** | 外部 HTML 不可控，**不强制改**；仅在插件 HTML 本身宽度合理时自然全屏。文档标注"插件邮件宽度由插件作者负责" | — |

### 4.3 签名位置统一
`inject_signature_inline` 当前是尾部追加（第 563 行）。路径 3 改为在 `_wrap_content_responsive` **包裹前**注入签名，使签名落在 90% 内容列内（与周报体验一致）。

## 五、为什么选"复用幽灵单元格 90%"而非"只改 max-width 数值"

| 候选方案 | 做法 | 结论 |
|----------|------|------|
| A（采用） | 抽 `_wrap_content_responsive`，全路径 90% 幽灵单元格 | Outlook/Foxmail/手机/Gmail 全稳，与周报已验证一致，唯一可靠 |
| B | 把 `max-width:680` 调大到 900 | Outlook 仍忽略 max-width→偏左；只是把能识别的客户端调宽，**未根治** |
| C | 内层去宽度、靠 3210 frame | 仅覆盖 3210 场景，路径 3 默认 Markdown 仍窄；且不统一 |

→ 选 **A**：与周报同源、可回归、一处维护。

## 八、回退与风险

- **回退**：代码改动单文件可 git revert；3210 模板 frame 改造前先备份原 `bodyTemplate`，异常还原。
- **风险 R1**：3210 模板更新接口若需鉴权/无 PUT，则 T4 改为 3210 管理后台手工改（10 个模板，工作量可控）。
- **风险 R2**：3210 frame 改 90% 后，内层 `markdown_to_email_html(..., wrap=False)` 若未同步（T3 漏做），会出现"外层 90% + 内层仍 680px"→ 内层偏窄。T3/T4 必须成对验证。
- **风险 R3**：`_ALLOWED_ATTRS` 白名单须含 `align`/`width`/`height`（周报整改已补，复用无碍）。
