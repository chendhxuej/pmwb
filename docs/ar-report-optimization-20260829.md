# 重点工作周反馈内容与格式优化方案（2026-08-29）

> 现状：昨天已完成 mc-1~mc-4 及负责人牵头制改造（未提交），老大反馈当前周反馈在**内容**和**格式**上不满足实际收集场景，需重新评估优化。
> 状态：**待老大确认后实施**

---

## 一、当前缺陷（基于已改造代码的实际形态）

| 维度 | 现有形态 | 问题 |
|---|---|---|
| **月计划** | 仅在子项复选框里出现，和月/周计划/任务混在一起 | 月底收集时没有独立的"本月月计划完成情况 + 下月重点"入口 |
| **周计划** | 只有"本周完成/下周计划/风险"三块文本 + 子项勾选 | 没有**带出上周反馈的下周计划**作为"上周计划进展"参考，也没有与周计划表项形成"上周→本周→下周"的滚动链路 |
| **成员待办** | 只能勾选"已完成" | 当前未完成的成员任务没有"进展说明"字段；也无法在反馈时顺手录入新任务 |
| **交付物** | 反馈卡片里没有上传入口 | 专题有材料时要切到"交付物" tab 上传，和反馈流程割裂 |
| **格式** | 所有输入平铺在一个卡片里 | 负责人线下收集的信息多，平铺难填、难看、难归档 |

---

## 二、优化目标

把周反馈从"三块文本 + 勾选"改造成**"上周回顾 → 月计划 → 周计划 → 成员待办 → 交付物 → 风险 → 下周计划"**的负责人汇总表单。

核心原则：

1. **承上启下**：上周的 `下周计划` 自动成为本周的 `上周计划进展` 输入提示。
2. **分类清晰**：月计划、周计划、成员待办各自独立区域，互不混排。
3. **可增量可新增**：既能反馈现有任务进展，也能在反馈时新增成员任务。
4. **交付物一体**：反馈卡片内直接上传/关联交付物。
5. **负责人牵头不变**：仍只向工单负责人发请求，由负责人线下收集团队信息后统一录入归档。

---

## 三、内容模板（推荐）

| 区域 | 内容 | 数据来源/处理 |
|---|---|---|
| **A. 上周计划进展** | 只读展示上周反馈的 `next_summary`，并列出上周计划在途子项的当前状态（让负责人对照填写） | 后端查同工单上周（week-1）反馈记录 |
| **B. 月计划** | ① 当前月份月计划列表及状态勾选<br>② 月总结（仅在月底周显示）<br>③ 下月重点/下月月计划草案 | 后端按所选周归属月份筛选 `pmwb_key_work_monthly_plan`；月底判断按"所选周结束日是否在当月 25 日之后" |
| **C. 周计划** | ① 本周/当前未完成的周计划列表及状态勾选<br>② 下周新的工作计划文本 | `next_summary` 字段即"下周新的工作计划"；本周周计划从 `pmwb_key_work_weekly_plan` 读取 |
| **D. 成员待办** | ① 当前未完成成员任务列表 + 进展说明 + 状态更新<br>② 新增成员任务（标题/负责人/截止日/备注） | 未完成 task 状态 ∈ {not_started, in_progress, delayed} |
| **E. 交付物** | 本专题相关材料上传区（文件/截图） | 复用现有交付物上传能力，`source='feedback'` |
| **F. 风险/求助** | 风险、阻塞、需协调事项 | 复用 `risk_note` |
| **G. 整体进度 + 本周完成摘要** | 总进度滑块 + `done_summary` 综合摘要 | 复用现有字段 |

> 说明：并非所有字段都要新增数据库列，尽量复用现有 `pmwb_key_work_weekly_feedback` 的 `done_summary/next_summary/risk_note/progress/item_updates`，只新增一个 JSON 字段 `member_task_notes` 存储"每条未完成任务的进展说明"。

## 四、数据模型 & 接口改动

### 4.1 模型（可选）

| 表 | 改动 | 说明 |
|---|---|---|
| `pmwb_key_work_weekly_feedback` | 新增 `member_task_notes` TEXT(JSON) | 记录每条成员任务的进展说明：`[{task_id, note, status}]` |
| `pmwb_key_work_deliverable` | 可选新增 `weekly_feedback_id` FK | 如需在台账里反查本次反馈关联的交付物；若只按 `source='feedback'` 追溯，可不加 |

### 4.2 后端接口

| 接口 | 改动 |
|---|---|
| `GET /key-works/{id}/weekly-feedback-form?week=` | 返回增加 `last_week_feedback`（上周 next_summary + item_updates）、`is_month_end`、分组后的 `monthly_items`/`weekly_items`/`task_items`，每项带当前状态 |
| `POST /key-works/{id}/weekly-feedbacks` | 请求体增加 `member_task_notes`（进展说明）、`new_tasks`（新增任务数组）、`deliverable_ids`（本次反馈已上传交付物 ID 列表）；后端在**同一事务**内：写反馈、创建新任务、更新任务 note、更新子项状态 |
| 现有成员任务/交付物 CRUD | 前端在反馈卡片内直接复用已有接口或一次性走 feedback 提交接口 |

### 4.3 前端

| 改动 | 说明 |
|---|---|
| 反馈卡片改折叠面板 | `el-collapse` 分 A/B/C/D/E/F/G 七个区域，默认展开 A/C/D/G |
| 月计划区 | 月底周额外显示"本月月总结 + 下月重点"文本框 |
| 周计划区 | 只读展示"上周计划进展"；周计划项列表 + 下周新计划文本框 |
| 成员待办区 | 未完成 tasks 表格（状态下拉 + 进展输入）；底部 mini 表单新增任务 |
| 交付物区 | 内嵌 `el-upload` + 已上传列表，上传即调用现有交付物接口 |
| 提交后 | 同步刷新成员待办 tab / 交付物 tab / 月周计划状态 |

## 六、验收标准

1. 打开周反馈 tab，默认能看到"上周计划进展"只读块（前提上周已反馈）。
2. 月计划、周计划、成员待办分别独立展示，不混排。
3. 成员待办区可对每条任务写进展说明，并能新增任务；提交后真实创建任务并刷新成员待办 tab。
4. 反馈卡片内可上传交付物，提交后在交付物 tab 可见。
5. 月底周（所选周结束日 >= 当月 25 日）自动出现"本月月总结 + 下月重点"输入区。
6. pytest 全量通过（历史遗留失败除外），前端构建通过，puppeteer 穿测覆盖新区域。
