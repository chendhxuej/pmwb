> 评估日期：2026-09-03 ｜ 评估人：Vicky2号 ｜ 状态：**已确认，已实施完成（2026-09-03 真实服务验证通过）**
> 评估依据：后端 39 张表 / 26 个 router 全量扫描 + 数据库存量实测 + 前端 104 源文件扫描
> 老大已拍板：存储=项目内 uploads/material/ ｜ 分类=两级自定义+业务领域 ｜ 预览=全类型（含 pptx/zip）｜ 节奏=一次性做到好用

## 零、结论先行

| 判断项 | 结论 |
|---|---|
| **能不能做** | 能，且成本比想象低。核心是加一层索引，不是重建文件体系 |
| **存量迁移难度** | **极低**。实测存量只有 **27 个文件**，不需要写迁移工程，一次性同步脚本即可 |
| **要不要动现有 5 个上传点** | **不要大动**。用"非侵入扫描汇聚"兜底，避免回归风险 |
| **主要工作量** | 不在汇聚，在**预览能力**（xlsx 预览要从零写）和**前端页面** |
| **建议分期** | 三期：P0 索引+列表+下载（可用）→ P1 预览+分类上传（好用）→ P2 联动增强 |
| **最大风险** | 现有上传逻辑三处复制粘贴、无任何大小限制、无 MIME 校验 —— 新模块不能继承这些毛病 |

**一句话方案**：新建 `pmwb_material`（统一文件索引）+ `pmwb_material_category`（两级可增删分类树）两张表，物理文件不动只登记指针，抽一个 `utils/file_storage.py` 统一上传工具，前端照抄 `KnowledgeView.vue` 的骨架。

## 二、关键发现（这些事实直接决定方案取舍）

### 2.1 ⚠️ 现存 Bug：同名文件重复登记

实测工单 **#50 的 attachments 里有两条同名记录** `电视议价补收明细20260825.xlsx`，但磁盘只有一份。

根因：`routers/operation.py:143-152` 上传时 `open(fp,"wb")` 直接覆盖同名文件，但元数据 `atts.append(meta)` 是**无脑追加**，不去重。

> **影响**：资料库若只做"扫描汇聚"，会把这条脏数据带进来显示成两个文件，点其中一个下载正常、另一个也正常（同一路径），但删除时会误删/残留。
> **对策**：汇聚时按 `(source_type, source_id, rel_path)` 建唯一约束去重；同时建议 P1 顺手修掉这个上传 bug（3 行代码）。

### 2.2 存量极少 → 迁移不是重点，**增量汇聚才是**

27 个文件意味着：
- ❌ 不需要写"存量迁移工程"，一次性 sync 脚本（约 80 行）足够
- ✅ 真正的价值在**未来每次上传自动登记**，否则资料库上线即落后
- ✅ 数据量大不了，模糊搜索用 `LIKE` 全表扫完全够（MySQL utf8mb4 下 LIKE 本就忽略大小写），**不需要上全文索引**

### 2.3 知识中心不适合承载，但应该打通

| 判断项 | 结论 |
|---|---|
| 能管二进制文件吗 | ❌ `vault_sync` 只扫 `.md`；`list_notes` 主动跳过 attachment 目录；无下载/预览接口 |
| 分类可增删改吗 | ❌ `category` 是固定 6 值枚举，不支持用户自定义 |
| 结论 | **独立建模块**，但复用 `domain_code` 维度，可选通过 `pmwb_knowledge_link` 挂到领域主笔记 |

### 2.4 完全没有鉴权，CORS 全开

全站无 user 表、无 token、CORS `allow_origins=["*"]`。「上传人」靠前端 Form 传参。

> 本机自用可接受；若 `PUBLIC_BASE_URL` 要配公网，必须先补一层鉴权。**本期建议保持现状，不做鉴权**（避免范围蔓延）。

### 2.5 mammoth 已装但漏写进 `requirements.txt`

`services/requirement_stage.py` 依赖 mammoth，实测 venv 已装，但 `requirements.txt` 里**没有这一行**。换机器部署会直接 ImportError。

> 对策：本期顺手补上（1 行），或者统一改用零依赖的 `core/docx_convert.py`。

### 2.6 上传无任何限制，全量读入内存

所有上传点都是 `file.file.read()` 一次性读入，**无大小限制、无 MIME 白名单、无流式写盘**。新模块必须加 `MAX_UPLOAD_SIZE`（建议 100MB）+ 分块写盘。

## 三、方案设计

### 3.1 定位与边界

**做什么**：文件资产的统一索引 + 检索 + 预览 + 下载 + 手工归档。
**不做什么**：不做文件版本管理、不做协同编辑、不做权限体系、不做全文检索（LIKE 够用）。

**与知识中心的分工**：
```
知识中心 = 业务知识笔记（.md 为主，语义化内容）
业务资料库 = 文件资产（xlsx/docx/pdf/图片，二进制材料）
两者通过 domain_code 打通，不互相替代
```

### 3.2 数据模型（两张新表）

#### `pmwb_material_category` —— 分类树（可增删改）

```python
class PmwbMaterialCategory(Base):
    __tablename__ = "pmwb_material_category"
    id          = Column(Integer, primary_key=True)
    code        = Column(String(64), unique=True, nullable=False, comment="分类编码")
    name        = Column(String(128), nullable=False, comment="分类名称")
    parent_id   = Column(Integer, ForeignKey("pmwb_material_category.id"), nullable=True)
    sort_order  = Column(Integer, default=0)
    enabled     = Column(Boolean, default=True, comment="停用后不出现在下拉，历史数据保留")
    created_at  = Column(DateTime, default=now_cn)
    updated_at  = Column(DateTime, default=now_cn, onupdate=now_cn)
```

设计要点：
- **两级足够**（大类 → 子类），不搞无限层级
- 用 `enabled` 软停而非硬删，避免历史材料"分类丢失"
- 预置分类建议：`业务联系单 / 数据清单 / 汇报材料 / 操作手册 / 合同协议 / 会议材料 / 系统截图 / 其他`

#### `pmwb_material` —— 统一文件索引

```python
class PmwbMaterial(Base):
    __tablename__ = "pmwb_material"
    id          = Column(Integer, primary_key=True)

    # —— 分类维度 ——
    category_id = Column(Integer, ForeignKey("pmwb_material_category.id"), nullable=True)
    domain_code = Column(String(64), comment="复用 pmwb_business_domain，可空")

    # —— 来源汇聚（冗余存储，避免列表页 N 次联表）——
    source_type = Column(String(64), nullable=False,
        comment="operation_issue/research_issue/requirement/dev_deliverable/"
                "keywork_deliverable/req_manual/manual_upload")
    source_id   = Column(String(255), comment="业务对象 id")
    source_no   = Column(String(128), comment="冗余单号，如 issue_no / req_id，供搜索")
    source_title= Column(String(500), comment="冗余来源标题，供搜索与展示")

    # —— 文件元信息 ——
    file_name   = Column(String(500), nullable=False, comment="原始文件名（展示用）")
    stored_name = Column(String(500), nullable=False, comment="落盘名（uuid 前缀防覆盖）")
    storage_root= Column(String(16), default="uploads", comment="uploads | vault")
    rel_path    = Column(String(1024), nullable=False, comment="相对 storage_root 的路径")
    file_size   = Column(Integer, comment="字节")
    file_ext    = Column(String(32), comment="扩展名小写，如 xlsx")
    file_type   = Column(String(64), comment="MIME")

    # —— 管理字段 ——
    origin      = Column(String(32), default="manual", comment="manual 手工上传 | auto 汇聚登记")
    uploaded_by = Column(String(64))
    note        = Column(Text, comment="备注，参与搜索")
    tags        = Column(String(512), comment="逗号分隔标签")
    download_count = Column(Integer, default=0)
    created_at  = Column(DateTime, default=now_cn)
    updated_at  = Column(DateTime, default=now_cn, onupdate=now_cn)

    __table_args__ = (
        Index("idx_mat_source", "source_type", "source_id"),
        Index("idx_mat_category", "category_id"),
        Index("idx_mat_domain", "domain_code"),
        Index("idx_mat_ext", "file_ext"),
        UniqueConstraint("source_type", "source_id", "rel_path", name="uk_mat_dedup"),
    )
```

**为什么只存指针、不搬文件**：
1. 现有 5 个模块的下载/删除逻辑都依赖原路径，搬了就全得改，回归风险大
2. 存量只有 27 个文件，搬迁收益为零
3. `uk_mat_dedup` 唯一约束顺手解决 2.1 的重复登记问题

### 3.4 预览能力矩阵（老大已选：全类型）

> 环境实测：LibreOffice ❌ 未装 ｜ WPS ✅ 已装（不用于服务端转换）｜ python-pptx ❌ 未装 ｜ openpyxl ✅ 已有 ｜ mammoth ✅ 已装

| 类型 | 方案 | 保真度 | 依赖 | 工作量 |
|---|---|---|---|---|
| **xlsx / csv** | openpyxl 读单元格 → 生成 HTML `<table>`，多 sheet 分页签 | **高**（数值/文本完整） | openpyxl ✅ 已有 | 新写 ~100 行 |
| **docx** | mammoth 转 HTML（抄 `requirement_stage.py:581`） | **高**（含图片/表格/样式） | mammoth ✅ 已装 | 抄现成 10 行 |
| **pdf** | `FileResponse(media_type="application/pdf")` inline | **100%** | 无 | 5 行 |
| **png/jpg/gif/bmp/webp** | 直接返回图片流，前端 `<img>` | **100%** | 无 | 5 行 |
| **txt / md** | 读文本 → `MarkdownRender`（md）或 `<pre>`（txt） | **高** | 无 | 10 行 |
| **htm / html** | 直接返回，前端 iframe `sandbox` 隔离 | **100%** | 无 | 5 行 |
| **zip** | `zipfile` 列清单：文件名 / 大小 / 压缩率 / 目录树 | **清单级**（不解内容） | 标准库 | ~50 行 |
| **pptx** | ⚠️ 见下方专项说明 | **内容级** | python-pptx（需装） | ~90 行 |
| **其他（rar/7z/exe 等）** | 元信息卡片（名称/大小/类型/上传时间）+ 下载按钮 | 无 | 无 | 5 行 |

#### ⚠️ pptx 预览专项说明（老大会关心的取舍）

真正的"所见即所得"PPT 预览只有两条路，本机**都不具备**：

| 方案 | 现状 | 评价 |
|---|---|---|
| LibreOffice headless 转 PDF | ❌ 未装，需下载安装 400MB+ | 高保真，但环境成本高、单次转换 3-8 秒 |
| WPS 命令行转换 | ✅ 已装 WPS | **不采用**：命令行转 PDF 非官方支持，会弹 UI/需激活，服务端调用会干扰老大日常使用 |
| 前端 CDN PPTXjs | 需外网 CDN | 纯前端，效果较好，但复杂母版/图表支持一般，离线环境失效 |

**本方案采用：python-pptx 提取式预览**（装一个轻量纯 Python 依赖，约 10MB）
- 逐页提取：所有文本段落（含层级/项目符号）+ 嵌入图片（base64 内嵌）+ 表格
- 渲染成「分页卡片」，每页显示页码、标题、文本块、图片、表格
- **能看清全部内容，但不还原真实排版位置**（看不到母版版式、动画、图表矢量）
- 页面上明确标注「简化预览，排版以原文件为准」+ 提供下载原件按钮

> 若老大后续需要高保真，再单独装 LibreOffice 走 PDF 路线，接口不用改（`/preview` 按扩展名分支）。

### 3.5 汇聚策略：扫描式，非侵入

**触发方式**：手工点"同步"按钮 + 后端启动时不扫描（避免拖慢启动）。数据量小，全量扫 < 1s。
