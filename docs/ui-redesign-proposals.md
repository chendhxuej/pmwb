# PMWB 表单密集型模块 UI 重设计方案

> 📌 **文档状态：提案（未整体采纳）**。方案中的抽屉统一宽度、抽屉草稿持久化（`useDrawerDraft`）等局部改进已落地，整体表单骨架重构尚未实施。

> 阶段：评估 + 设计方案 + 可交互 SVG 原型（**暂不动代码**）。
> 范围：以「统一表单骨架」示例覆盖所有模块，体现通用性。
> 配套可交互原型：`../prototype/ui-redesign-prototype.html`（点击切换「当前 / A / B / C」与不同模块场景，直观体验差异）。

---

## 0. 背景与目标

PMWB 各业务模块（需求交付、重点工作、会议、运营工单、知识中心、SQL 脚本库）都重度依赖表单展示与编辑，但当前实现存在「信息找不到、操作路径深、横向浪费、视觉不统一」四类问题，访问便捷性差。

本次目标：重新评估当前设计，给出 **至少两套** 可落地的 UI 设计方案，并用可交互 SVG 原型辅助决策。

---

## 1. 当前状态评估（六大核心问题）

表单密集型模块普遍采用「`el-dialog` 单列表单 + `el-drawer` 竖直分段堆叠 + 横向溢出 tabs」组合，核心问题：

1. **横向 tab 溢出**：`KeyWorkView` 10 段在 860px 抽屉内横向溢出，无概览，切 tab 丢失滚动位置。
2. **长滚动疲劳**：详情/工作流抽屉竖直堆叠、无目录锚点，用户在一长串 section 里找不到目标。
3. **dialog 嵌套深**：子表编辑大量并列 `el-dialog`（`KeyWorkView` 约 9 个，宽 480–520px 单列），上下文丢失、操作路径深。
4. **无进度概览**：缺整体完成度/字段概览，无「保存即下一步」机制，保存按钮分散在各卡片。
5. **横向浪费**：单列表单浪费空间，`label-width` 在 80~100px 间混用、不统一。
6. **令牌三处冲突**：`design.css`（圆角 10/16/22、蓝 `#2f6fed`）/ `main.css`（圆角 4px）/ `MainLayout.vue` scoped（`#304156`、`#f5f7fa`）三套样式源打架，视觉不统一。

---

## 2. 统一设计规范建议（落地前置，先记结论）

无论选哪套方案，先收敛基础规范，避免新组件建在冲突令牌上：

1. **收敛令牌**：统一以 `design.css` 为主（`--accent:#2f6fed`、圆角 10/16/22）；弃用 `main.css` 的 4px 圆角与 `MainLayout` scoped 的 `#304156`/`#f5f7fa`，侧栏统一 `#1e293b`。
2. **统一字段网格**：`label-width: 110px`，表单容器 2 列（`el-row`/`el-col :span=12`），`gap: 16px`。
3. **统一抽屉档位**：详情 `860px` / 工作流 `78%` / 速编 `360px`（mini 面板）。
4. **引入统一基座**：优先落地 `FormShell + SectionNav` 作为「统一表单骨架」，再逐模块迁移。

---

## 3. 三套设计方案

### 方案 A — 锚点目录 + 双栏 Bento 表单骨架（★ 推荐作基座）

- **核心思想**：用左侧 sticky 竖向分段导航替代横向溢出 tab；右侧双栏网格承载表单，全程可见「我在哪、还差哪」。
- **布局草图**：

  ```
  ┌────220────┬────────────flex────────────┐
  │ ① 基本信息│  右栏：FieldGrid 2列        │
  │ ② 目标 ✓  │  ┌──────┐ ┌──────┐         │
  │ ③ 验收 ●  │  │field │ │field │         │
  │ ④ 里程碑  │  └──────┘ └──────┘         │
  │ ... 10段   │  ┌──────┐ ┌──────┐         │
  │ [进度 40%] ├───────────────────────────┤
  │            │ footer: 保存 | 上一段 | 下一段 │
  └────────────┴───────────────────────────┘
  ```
- **交互模型**：scroll-spy 高亮当前段；点 nav 平滑滚动到对应区；子表改为**同壳内联编辑**（不再开独立 dialog）；未过校验段标红。
- **需引入组件**：`FormShell`（统一壳/网格/footer）、`SectionNav`（sticky 导航 + 完成度标记）、`FieldGrid`（2 列，label-width=110）、`InlineSubTable`（内联子表）。
- **适用**：KeyWork / Meeting / WorkOrder / SqlScript 的详情与编辑。
- **优劣**：信息密度高、导航清晰、彻底治理溢出；超长仍滚动（靠 nav 跳转缓解）。**迁移成本：中**。

### 方案 B — 分步向导 + 概览看板

- **核心思想**：进入模块先弹「概览看板」展示各段完成状态，再走带进度%的竖向 stepper，「保存并下一步」。
- **布局草图**：

  ```
  ┌─ 概览看板（入口）──────────────┐
  │ [基本信息 ✓][目标 ✓][验收 ○]…   │ 点卡片直达
  └───────────────────────────────┘
  ┌──220──┬──────────flex──────────┐
  │①采集  │  当前步表单（单步聚焦）  │
  │②评估  │  ┌──────┐ ┌──────┐     │
  │③故事● │  │field │ │field │     │
  │④生成  │  └──────┘ └──────┘     │
  │ 进度60%├───────────────────────┤
  │        │ footer: 保存并下一步    │
  └────────┴───────────────────────┘
  ```
- **交互模型**：分步必填校验、保存即下一步、上一步回填、概览卡片点段直达。
- **需引入组件**：`StepWizard`、`OverviewBoard`、`StepPane`。
- **适用**：RequirementDelivery 4 步、WorkOrder 5 步等强流程模块。
- **优劣**：引导强、进度可视、认知负荷低；弱全貌、步骤多时来回切。**迁移成本：中高**（需重构保存逻辑为逐步持久化）。

### 方案 C — 可折叠分区 + 侧边速编

- **核心思想**：`el-collapse` 分区，每段可展开；编辑开右侧 360px mini 面板（非全屏 overlay），保留上下文。
- **布局草图**：

  ```
  ┌──collapse 段列表────┬──360 mini 编辑──┐
  │ ▸ 基本信息（展开）   │ 字段1 [输入]    │
  │    ├ 字段行          │ 字段2 [输入]    │
  │ ▸ 目标              │ [保存]          │
  │ ▸ 验收标准          ├─────────────────┤
  │ ...                 │ 上下文不被遮挡   │
  └─────────────────────┴─────────────────┘
  ```
- **交互模型**：段展开/折叠；点行开右侧 mini 面板原地编辑；全局 sticky 保存。
- **需引入组件**：`AccordionPanel`、`MiniEditor`、`ContextBar`。
- **适用**：长详情浏览 + 零散编辑（Meeting / WorkOrder 详情）。
- **优劣**：上下文不丢、迁移最轻（复用 `el-collapse`）；mini 空间小、并行编辑受限。**迁移成本：中**。

## 4. 方案对比表

| 维度 | 当前 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|---|
| 信息密度 | 中（单列浪费） | **高（双栏）** | 中（单步聚焦） | 中 |
| 导航/概览 | 差（无锚点/tab溢出） | **强（sticky nav+进度）** | **强（概览+stepper%）** | 中（折叠） |
| 溢出治理 | 失败 | **根治** | 根治 | 根治 |
| 流程引导 | 弱 | 中 | **强** | 弱 |
| 上下文保留 | 差（dialog 遮挡） | 中（同壳） | 中（同壳） | **强（mini 面板）** |
| 迁移成本 | — | 中 | 中高 | 中（最轻量） |
| 最佳适用 | — | 详情/编辑型 | 强流程型 | 浏览+零散编辑 |

## 5. 模块 → 方案推荐映射

| 模块 | 类型 | 推荐 | 说明 |
|---|---|---|---|
| 重点工作 KeyWork | 详情/编辑（10段） | **A**（优先试点） | 10 段溢出最严重，A 治理最直接 |
| 会议 Meeting | 详情（5段） | A 或 C | 浏览多→C；要编辑效率→A |
| 运营工单 WorkOrder | 详情+状态流 | A 或 B | 状态流强→B；纯详情→A |
| 需求交付 Requirement | 强流程（4步） | **B** | stepper+概览最契合 |
| SQL 脚本库 | 表单+代码 | **A** | 双栏 + 内联高亮编辑 |
| 知识中心 | 浏览型 | 保持现状 | 树+卡片已清晰，无需重做 |

## 6. 可交互原型使用说明

打开 `prototype/ui-redesign-prototype.html`：

1. **顶部「场景切换」**：统一骨架（10 段示例）/ 重点工作 KeyWork（10 段）/ 需求交付（4 步工作流）。
2. **左侧「方案切换」**：当前 / 方案 A / 方案 B / 方案 C —— 点击即重绘对应 SVG 线框。
3. **交互体验**：
   - 方案 A：点左侧导航项 → 右侧内容高亮并滚动到对应段，底部进度条联动。
   - 方案 B：点竖向 stepper → 切换当前步表单；点「概览」→ 切到完成状态看板。
   - 方案 C：点段标题 → 展开/折叠；点字段行 → 右侧 mini 面板打开。
   - 当前：可观察 tab 溢出、长滚动、嵌套 dialog 等痛点。

## 7. 后续落地路线（确认方案后）

1. 收敛 `design.css` 令牌，统一 `label-width=110` 与抽屉档位（规范第 2 节）。
2. 落地基座组件 `FormShell + SectionNav`（方案 A 核心），先以 **KeyWork 10 段** 试点验证。
3. 按第 5 节映射，逐模块迁移；强流程模块（需求/工单）评估是否叠加方案 B 的 stepper。
4. 每迁移一个模块走完整验证：pytest / vitest / 双端 build / 浏览器无头冒烟。

> 本方案文档为决策材料，确认选型后再进入实现；实现阶段另开任务，不在此文档范围内。
