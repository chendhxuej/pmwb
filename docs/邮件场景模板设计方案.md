# PMWB 邮件场景模板设计方案

> 状态：设计稿 | 日期：2026-08-17 | 关联：邮件发送能力统一规划设计方案.md

## 1. 现状诊断

### 1.1 SCENES 注册表（12 场景）

当前 `backend/services/mail_dispatch.py` 的 SCENES 注册表中，**全部 12 个场景均为 `raw=True`**，即正文由前端/后端代码构建 Markdown，后端只做 Markdown→HTML+签名注入，不走 3210 模板渲染。

### 1.2 3210 现有模板（5 个）

| 模板名 | type | 变量 | 格式 | SCENES 是否引用 |
|--------|------|------|------|----------------|
| 会议通知 | `meeting_notice` | meetingTopic, meetingTime, meetingLocation, host | html | ❌ scene 有此 key 但 raw=True |
| 任务督办提醒 | `task_reminder` | taskTitle, assignee, status, planEnd | html | ❌ scene 有此 key 但 raw=True |
| 需求催办通知 | `xqemail_reminder` | reqId, reqName, saName, proposeTime, items | text | ❌ |
| 需求评估通知 | `req_eval` | 需求编码, 需求名称, ... (中文键) | text | ❌ |
| Obsidian笔记同步 | `obsidian_note` | title, content | html | ❌ |

### 1.3 核心问题

1. **模板与场景脱节**：3210 有 5 个模板但 SCENES 一个都没引用，全部走 raw markdown
2. **变量命名不统一**：camelCase（reqId）与中文（需求编码）混用
3. **正文逻辑分散**：前端 6 个 .vue 文件各自 `buildBody()`，后端 3 个 service 各自拼正文
4. **运营模块遗漏**：WorkOrderView/RequirementDeliveryView 原用独立 SuperviseDialog，P2 已收口

## 2. 场景分类与改造策略

### Phase 1：启用已有 3210 模板（3 场景）

这 3 个场景 3210 已有对应 type 的模板，只需：后端 SCENES 改 `raw=False` + 设置 `template_key` + 统一变量名。

| 变量名 | 类型 | 说明 | 示例 |

| meetingLocation | string | 会议地点 | 会议室A / 腾讯会议123 |

### Phase 2：3210 新建模板（7 场景）

这 7 个场景 3210 没有对应 type 的模板，需要：在 3210 创建新模板 + 后端 SCENES 改 `raw=False` + 前端改传 variables。

#### 2.4 meeting_minutes（会议纪要）

- **3210 type**: `meeting_minutes`（新建）
- **变量 schema**:

| 变量名 | 类型 | 说明 |
|--------|------|------|
| meetingTitle | string | 会议主题 |
| meetingDate | string | 会议日期 |
| attendees | string | 参会人员（逗号分隔） |
| content | string | 纪要正文（Markdown/HTML） |
| actionItems | string | 行动项列表（格式化文本） |

- **3210 模板设计**:
  - subjectTemplate: `【会议纪要】{{meetingTitle}} ({{meetingDate}})`
  - bodyFormat: `html`
  - bodyTemplate:
    ```html
    <div style="font-family:sans-serif;max-width:600px;margin:0 auto;">
      <h2 style="color:#1a1a3e;">{{meetingTitle}}</h2>
      <p><strong>日期：</strong>{{meetingDate}}</p>
      <p><strong>参会人：</strong>{{attendees}}</p>
      <hr>
      <div>{{{content}}}</div>
      {{#actionItems}}
      <h3>行动项</h3>
      <div>{{{actionItems}}}</div>
      {{/actionItems}}
    </div>
    ```
- **调用方**：`backend/services/meeting.py` → `send_meeting_email(scene="meeting_minutes")`

#### 2.5 action_dispatch（行动项派发）

- **3210 type**: `action_dispatch`（新建）

| 变量名 | 类型 | 说明 |
|--------|------|------|
| meetingTitle | string | 会议主题 |
| actions | string | 行动项列表（格式化 HTML） |

- **3210 模板设计**:
  - subjectTemplate: `【任务派发】{{meetingTitle}}`
  - bodyFormat: `html`
  - bodyTemplate:
    ```html
    <div style="font-family:sans-serif;max-width:600px;margin:0 auto;">
      <h2 style="color:#1a1a3e;">会议行动项派发</h2>
    ```

#### 2.6 action_supervise（行动项督办）

- **3210 type**: `action_supervise`（新建）
- **变量 schema**:

| 变量名 | 类型 | 说明 |
|--------|------|------|
| owner | string | 负责人姓名 |
| content | string | 行动项内容 |
| dueDate | string | 截止日期 |
| status | string | 当前状态 |
| scene | string | urge/sync（催办/同步） |

- **3210 模板设计**:
  - subjectTemplate: `{{#if scene=urge}}催办{{else}}同步{{/if}}：{{content}}`
  - 简化方案：前端传 subject，模板只管 body
  - bodyFormat: `text`
  - bodyTemplate:
    ```
    {{owner}}：

    以下会议行动项需要{{sceneLabel}}，详情如下：
    - 行动项内容：{{content}}
    - 负责人：{{owner}}
    - 截止日期：{{dueDate}}
    - 当前状态：{{status}}

    请及时处理并反馈进展，辛苦了！
    ```
- **调用方**：前端 `MeetingActionsView.vue` → scene 模式 → `/mail-dispatch/send`

## 3. 变量命名规范

### 3.1 统一规则

- **所有变量使用 camelCase**：如 `meetingTitle`、`reqId`、`saName`
- **禁止中文变量名**：3210 现有 `req_eval` 模板使用中文键（需求编码、需求名称），需重构为 camelCase
- **日期格式**：统一 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm`
- **列表变量**：传入格式化好的字符串（3210 模板引擎不支持循环）

### 3.2 变量映射表

| 场景 | 前端当前字段 | → | 统一变量名 |
|------|-------------|---|-----------|
| meeting_notice | meeting.title | → | meetingTopic |
| meeting_notice | meeting.start_time | → | meetingTime |
| meeting_notice | meeting.location | → | meetingLocation |
| meeting_notice | meeting.host | → | host |
| task_reminder | task.title | → | taskTitle |
| task_reminder | task.assignee | → | assignee |
| task_reminder | task.status | → | status |
| task_reminder | task.plan_end | → | planEnd |
| requirement_reminder | req.req_id | → | reqId |
| requirement_reminder | req.req_name | → | reqName |
| requirement_reminder | req.sa_name | → | saName |
| supervise_urge | row.issue_no | → | no |
| supervise_urge | row.title | → | title |
| supervise_urge | row.handler | → | handler |
| supervise_urge | row.resolve_date | → | resolveDate |

## 4. 实施路线图

### 4.1 Phase 1 实施步骤（启用已有模板）

1. **3210 侧**：更新现有 3 个模板的变量名为 camelCase（req_eval 模板的中文键需重构，但本场景不直接使用该模板，暂不动）
2. **后端**：SCENES 注册表修改 3 个场景 → `raw=False` + 设置 `template_key`
3. **后端**：各调用方 service 代码改为传 variables dict 而非 body
4. **前端**：对应页面的 `buildBody()` 函数改为构建 variables 对象
5. **测试**：pytest 验证 + 前端 build + 浏览器冒烟

### 4.2 Phase 2 实施步骤（新建模板）

1. **3210 侧**：通过 `POST /api/templates` 创建 7 个新模板（设置 type、subjectTemplate、bodyTemplate）
2. **后端**：SCENES 注册表修改 7 个场景 → `raw=False` + 设置 `template_key`
3. **前端**：6 个页面的 `buildBody()` 改为构建 variables 对象传给 MailComposeDialog
4. **MailComposeDialog**：scene 模式下自动将 variables 传给 `/mail-dispatch/preview` 和 `/mail-dispatch/send`
5. **测试**：同上

### 4.3 Phase 3 说明

- work_report 和 plugin 保持 `raw=True`，无需改 SCENES
- 签名通过 `inject_signature_inline` 统一注入，已有实现
- 后续如需模板化 work_report，可创建 `{{{content}}}` 透传模板

## 5. 风险与约束

1. **3210 模板引擎限制**：不支持条件分支和循环，列表需在调用方格式化为字符串后传入
2. **变量重命名风险**：3210 现有模板可能被其他系统引用，重命名需确认影响面
3. **降级机制**：3210 不可用时，`_render_mail` 已有 fallback 到 raw markdown 逻辑，需确保每个场景有合理的 fallback_template
4. **预览一致性**：`/mail-dispatch/preview` 和 `/mail-dispatch/send` 共用 `_render_mail`，保证「预览即实发」
