## 1. 设计原则（科学标准基线）

参考 PARA 区域管理、Zettelkasten 原子笔记、MOC（内容地图）、企业知识管理（KM）本体论与知识图谱建模，确立 6 条原则：

1. **单一事实源**：Obsidian 笔记是唯一权威，数据库只索引/登记关联，绝不另建平行知识库。
2. **领域为中枢**：`domain_code` 是唯一主轴，所有知识、事件、过程都挂在某个业务领域下。
3. **主笔记 = 业务 MOC（HUB）**：每个领域一份主笔记，聚合该业务全貌；子笔记是**原子知识**，可独立链接与复用。
4. **类型化原子笔记**：每种知识有明确定义的类型与 frontmatter schema（见 §3），保证结构化、可检索、可聚合。
5. **关联即数据**：所有跨实体关系进 `pmwb_knowledge_link`，并带 `event_type` / `event_date` / `summary`，使"时间线"成为可查询的一等公民。
6. **自动回流 + 人不被覆盖**：过程模块事件 → 沉淀引擎 → 回写主笔记"自动区" + 登记 link；主笔记"人工区"（概述/SOP 概览）系统绝不自动改写。

## 2. 信息架构（目录树 · 科学分层）

取消原 `03-业务规则` 与 `05-交付物` 编号冲突，重排为清晰分层：

```
01-业务知识/
  {domain_group}/                      # 业务大类（如 商客/家客/政企专线）
    {domain_name}/                     # 业务领域（domain_code 对应，业务中枢）
      {domain_name}.md                 # ★ 主笔记 / 业务 HUB（MOC）
      02-产商品体系/                    # 产品、资费、产商品规格（原子笔记 type=product）
      03-业务流程/                      # 流程图、环节说明（type=process）
      04-业务规则/                      # 场景规则、校验规则（type=rule），自动聚合区
      05-操作手册/                      # SOP、操作指引（type=manual）
      06-交付物/                        # 需求交付物文件（操作手册等，type=delivery）
      07-会议决议/                      # 会议纪要关联（type=meeting）
      08-专题与案例/                    # 专项运营、问题案例（type=topic / operation_ticket）
```

要点：
- 主笔记文件名统一 `{domain_name}.md`，作为该业务唯一的"门面"与 MOC。
- 子目录编号即知识类型分区，与原子笔记 `type` 一一对应，便于自动归档与聚合。
- `domain_code` 缺失时安全回退到 `{group}/{name}` 旧路径（沿用 `obsidian_paths.resolve_domain_path`）。

## 3. 原子笔记类型体系（标准 schema）

所有子笔记统一 frontmatter，保证可检索、可聚合、可时间线化：

```yaml
---
type: requirement | operation_ticket | meeting | product | process | rule | manual | delivery | topic
domain_code: 一网通宽带
source_id: REQ-2026-0811
event_date: 2026-08-11          # 过程事件发生日（需求上线日/会议日/工单完成日）
title: 一网通融合开通流程优化
tags: [融合开通, 团单]
owner: 陈大海
status: active                  # active | archived
generated_by: system | manual   # 自动沉淀 or 手工
---
```

各类型标准模板（节选核心章节，系统沉淀时按此生成骨架，人工补充细节）：

| type | 核心章节 | 沉淀来源 |
|------|----------|----------|
| `requirement` 需求 | 背景/目标/范围/涉及产商品/流程变更/规则变更/交付物/验收 | 需求模块关闭或定稿 |
| `operation_ticket` 运营工单 | 问题描述/影响业务/处理过程/结论/预防措施 | 运营工单完成 |
| `meeting` 会议 | 议题/决议/待办/关联业务/参会 | 会议结束 |
| `product` 产商品 | 名称/资费/适用客户/开通流程/关联系统/版本 | 需求产商品变更 or 手工 |
| `process` 业务流程 | 环节/角色/系统/异常分支 | 需求流程变更 or 手工 |
| `rule` 业务规则 | 触发条件/判定逻辑/处理动作 | 用户故事规则 or 手工 |
| `manual` 操作手册 | 步骤/SOP/注意事项/截图 | 交付物 or 手工 |
| `delivery` 交付物 | 文件链接/版本/说明/关联需求 | **需求直接挂载的文件**（不再经开发工单） |
| `topic` 专题/案例 | 背景/分析/结论/经验 | 运营沉淀 or 手工 |

## 5. 关联与时间线模型（反向看历史）

`pmwb_knowledge_link` 扩展（向后兼容现有字段）：

| 字段 | 含义 |
|------|------|
| source_type | requirement / operation_ticket / meeting / delivery / rule / manual |
| source_id | 源记录主键 |
| domain_code | 业务领域（中枢） |
| link_type | main（回链主笔记）/ sub（子笔记）/ ref（引用） |
| event_type | 同 source_type，用于时间线分组着色 |
| event_date | **过程事件发生日**（需求上线日/会议日/工单完成日），时间线主键 |
| summary | 一句话摘要，时间线叙事用 |
| note_path | Obsidian 笔记相对路径 |
| created_at | 登记时间 |

新增接口：
- `GET /api/v1/knowledge/business-timeline?domain_code=&from=&to=` → 按 `event_date` 聚合的事件序列（支撑"该业务各时间点干了什么"）。
- `POST /api/v1/knowledge/sync-main-note` → 触发 §4 主笔记自动区回流。

## 6. 自动化 / 半自动沉淀机制（已去开发工单）

| 触发 | 动作 | 登记 link（event_type / event_date） |
|------|------|----------------------------------------|
| **需求关闭 / 定稿** | 建需求子笔记 → 解析产商品/流程/规则变更 → 回写主笔记自动区 → 归档交付物 | requirement / 上线日 |
| **需求交付物（操作手册等文件）** | **直接挂在需求上的文件** → 复制至 `06-交付物/` → 登记主笔记 §6 | delivery / 交付日 |
| **会议结束** | 纪要生成 → 选 domain → 沉淀 `07-会议决议/` | meeting / 会议日 |
| **运营工单完成** | 关联 domain → 沉淀 `08-专题与案例/` | operation_ticket / 完成日 |
| **半自动：速记收件箱** | 手动选 domain+type → 一键生成原子笔记骨架 | 按类型 / 录入日 |

> 取消项：`sediment_dev_ticket`、`05-交付物` 对开发工单的依赖、`pmwb_dev_ticket` 作为沉淀源。操作手册交付物改为"需求直接挂载文件"归档，无需开发工单中间实体。

## 7. 知识中心 UI（以业务为中心的 3 视图）

收敛原 5 个脱节 Tab（知识库/产品圣经/知识沉淀/按领域/SQL脚本库）：

1. **业务全景 HUB（核心）**
   - 左侧领域树（消费 `pmwb_business_domain`）；
   - 右侧渲染主笔记（概述 + 各自动区）+ **业务时间线组件**（§5 接口驱动）；
   - 产品圣经取消硬编码 `PRODUCT_BIBLE`，改为"主笔记 §2 产商品体系"的呈现，产品圣经=领域主笔记的产商品视图。
2. **知识检索**
   - 收编原"知识库"Tab：跨领域全文 + 类型/标签/domain/时间过滤；
   - 结果可跳主笔记或原子笔记。
3. **沉淀向导**
   - 替换错配的"知识沉淀"Tab：速记收件箱 + 一键沉淀 + 关联 domain 选择；
   - **SQL脚本库保留在知识中心**：补齐 `domain_code` 关联（每条脚本标注所属业务领域），纳入"知识检索"可发现资源，不再是无关联的资产。

## 10. 主笔记回写策略（评估决策）

按"业务事实不可被误写 + 结构化数据可信"原则，对主笔记自动区做**分级回写**：

| 回写区 | 触发条件 | 理由 |
|--------|----------|------|
| §2 产商品体系 | 仅"**已上线（go_live）+ 带产商品变更标记**"的需求 | 产商品是业务事实，草稿/未上线需求回写会污染权威源 |
| §3 业务流程 | 仅"**已上线 + 带流程变更标记**"的需求 | 同上 |
| §4.1 场景规则 | 用户故事含 `rules` 字段即回写（按 `### REQ-xxx` 分段） | 来自结构化字段，带需求编号可追溯，风险低 |
| §6 交付物 | 需求直接挂载的文件即归档回写 | 文件是确定交付物，无可争议 |
| §8 业务时间线 | **所有** link（需求/会议/工单/交付）均进入 | 时间线即"做过什么"的客观记录，不分保守 |
| §1 概述 / §4.2 通用规则 / §7 关联系统 | **永不自动回写** | 人工区，系统只生成不覆盖 |

> 安全兜底：任何自动回写均写入"自动区"，重算即刷新；人工区文字零触碰。回写前校验 `domain_code` 非空且领域主笔记存在（否则经 `ensure_domain_main_note` 建骨架）。
