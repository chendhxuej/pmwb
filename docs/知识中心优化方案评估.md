# PMWB 知识中心模块优化方案评估

> 评估日期：2026-08-30 ｜ 评估人：Vicky2号 ｜ 触发：老大要求"从整个项目角度重新分析、参考同类方案、制定优化改进方案或重新构建"
> 配套调研：后端现状探查（3 份）、前端现状探查（1 份）、vault 实际规模统计、同类方案 Web 调研（企业 AI 知识中台 / PKM 自动生长 / Obsidian 原生能力）

---

## 0. 一句话结论

知识中心现在不是"业务知识自动汇聚中台"，而是一个**半手工的文件堆砌器**：汇聚 100% 靠人工点击、路径/索引权威源混乱、双份实现互相打架、前端业务全景破损、检索弱、LLM 只做消费侧。

**推荐路径：保留 Obsidian 作为存储底座（数据主权），重构"汇聚层 + 知识层 + 呈现层"，分阶段小步快跑。不是推倒重来，是治理 + 升级。**

## 1. 现状诊断（乱在哪，含证据）

### 1.1 汇聚严重依赖人工，覆盖率极低（核心病灶）

| 事实 | 证据 |
|---|---|
| 全系统 **0 个自动归档调度器**（无 APScheduler / cron / 定时任务） | grep `apscheduler/cron/schedule.every` 零命中；唯一"自动"是请求内串联（上传手册→`archive_requirement_manual`→`sync_main_note_from_links`） |
| 15 个业务模块仅 **5 个**有沉淀出口 | 仅 运营/会议/需求/用户故事/开发工单 有 sediment 端点 |
| 知识库 `pmwb_knowledge_item` 仅 **115 条** | `source_type` 分布：manual 38 / vault_sync 40 / meeting 25 / requirement 11 / operation **1** |
| **AI 总结 66 篇完全游离索引**（最大暗数据） | `work_report.py:_archive_to_obsidian` 只落盘 `15-工作总结/{类型}/{日期}.md`，**不建 knowledge_item**，不触发沉淀 |
| 重点工作（10 张表）、一线调研、SQL 脚本库、待办、主动优化、邮件记录：**零沉淀出口** | 探查确认无 sediment 函数、无索引写入 |

### 1.2 路径权威源与真实 vault 割裂（混沌根源）

| 事实 | 证据 |
|---|---|
| `domain_code.vault_path` 写了虚构中间层 | 库里写 `01-业务知识/政企业务知识库/商客业务/一网通宽带`，真实目录是 `01-业务知识/商客业务/一网通宽带`（**无"政企业务知识库"层**，实际不存在） |
| **4 套路径规则并存** | ① 领域树 `obsidian_paths.py`（`01-业务知识/{group}/{name}/`）② legacy 硬编码 `11-业务运营/`、`05-会议纪要/`、`14-知识沉淀/开发交付`、`10-业务建设/业务规则` ③ 同置路径（需求自身文件夹）④ `15-工作总结/` |
| 后果 | 文件散落多目录、与领域树割裂；反向同步 `vault_sync` 只扫 `enabled AND vault_path!=''` 的领域 → 大量笔记永不入索引 |

### 1.3 双份实现、互相打架

| 事实 | 证据 |
|---|---|
| `services/knowledge_link.py`（早期版，"## 关联对象"章节）vs `services/knowledge_link_service.py`（1026 行，frontmatter `related_*` + §7 索引）**两套都回写同一批文件** | `routers/knowledge.py` 同时 import 两边 → `/links` 与 `/{item_id}/links` 语义不同、行为不一致 |
| 需求沉淀端点重复 | `POST /knowledge/sediment/requirement/{id}` 与 `POST /obsidian/sediment/requirement/{id}` 调同一函数 |
| **主笔记 §10 永不落盘** | `build_main_note_markdown()` 只生成到 §9，`MAIN_NOTE_SECTIONS` 却定义了 14 项（含 §10 相关系统）→ 前端永远显示"暂无数据" |

### 1.4 前端业务全景"很乱"（直接可见的破损）

| 问题 | 证据 |
|---|---|
| 菜单只露 1 入口 | 7 个子路由仅 `hub` 可见，其余 6 个全 `meta.hidden:true`（只能深链） |
| HubPanel 是固定左右双栏，不是设计的"产品圣经+时间线" tab | `HubPanel.vue` `.hub-split` grid 1fr 1fr；`DomainKnowledgeView` 弹窗才是 tab |
| **3 处调用不存在的 API 必崩** | `KnowledgeView.createMainNote()`（api 无此法）、`ObsidianNoteDialog.getContent()`（实为 `getNoteContent`）、`KnowledgeItemLinker` 三方法 `listByItem/createItemLink/deleteItemLink`（均未定义） |
| 孤儿组件 / 假功能 | `SearchPanel.vue`、`SedimentPanel.vue` 零引用；`KnowledgeView.linkRequirement()` 只弹 toast 不发请求；`Math.random()` 前端生成业务主键 |
| 视觉割裂 | `DomainKnowledgeView.vue` 硬编码深色 `#1e1e2e`，全站浅色主题 |
| 空态堆砌 | HubPanel/DomainKnowledgeView/SearchPanel 大量 `el-empty`，DB 未初始化整页空 |

### 1.5 取数层重复、无统一服务

- `report_collector.py`（926 行）与 `task_center.py` 各自直连 11~13 张表，**全量 `.all()` + Python 内存过滤**，无 SQL 层分页/过滤（性能隐患），大量重叠实现。

### 1.6 检索弱、无智能加工

- 仅 `LIKE` + 内存打分，不搜 Obsidian 正文，无全文/向量索引。
- LLM 只做**消费侧**（生成报告/问答/故事）；`pmwb_knowledge_item.summary` 是 `[:200]` 截断、`tags` 是硬编码模板、`domain_code` 人工指定——**零生产侧加工**（无自动摘要/标签/归类/实体抽取）。

### 1.7 业务领域树本身混乱（老大 2026-08-30 补充，P0 核心前置）

> 老大明确：业务知识主笔记都应归在 `01-业务知识` 下、按正确分组管理，现在关联的很乱，需要**连 Obsidian 业务知识一起统筹设计和数据迁移整治**。

| 事实 | 证据 |
|---|---|
| 真实 vault 顶层分组（正确基准） | `公共能力 / 商客业务 / 系统平台 / 通用`（另混入 `家客业务知识库`、`其他政企业务知识库` 两个错误层） |
| DB `domain_group` 混入错误分组 | 取值含 `政企业务`（6 个）、`商客业务`（20）、`公共能力`（3）、`系统平台`（8）、`通用`（5）——"政企业务"应按业务归属归并 |
| `vault_path` 写了虚构中间层 | 大量写 `01-业务知识/政企业务知识库/商客业务/...`，真实目录无"政企业务知识库"层 → 双向对不上 |
| 领域命名重复/错放 | `一网通FTTO` vs `FTTO`、`商客和目` vs `和目业务`、`商客云无线` vs `云无线` 并存；`安防` 与 `商客安防` 并存 |
| 部分领域无 `vault_path` | 8 个 domain（general-group/mrljs/platform-group/rcgl/sk-hm/system-construction/ywt-zuw 等）`vault_path` 为 NULL，永不参与索引与沉淀 |

**结论**：路径权威源问题不只是"字段写错"，而是**领域树的分组口径与真实 vault 不一致**。整治必须把"领域分组标准 + vault 目录结构 + DB 字段"三者一起对齐，再做数据迁移。

## 2. 同类方案参考（提炼可借鉴点）

### 2.1 企业 AI 知识中台（三层架构 + 知识治理）

- **三层架构**：数据层（多源接入/治理/向量存储）→ 服务层（RAG/大模型/知识图谱/智能体）→ 应用层（场景化嵌入业务流）。
- **知识治理 "3-2-1"**：覆盖率 ≥85%、准确率 ≥95%、业务导向。
- **事件驱动实时 RAG**（Confluent 实践）：用 CDC/事件流取代 nightly batch，源系统变更（工单关闭、wiki 编辑、文档更新）即时更新，消除"过时知识"——直接对应我们"零自动归档"的病灶。
- **GraphRAG**：把碎片组织成关系网络，跨文档关联推理，输出带依据的结论（对应我们的"业务全景关联展示"诉求）。

### 2.2 PKM 自动生长（个人知识管理）

- **CODE 方法**：Capture（捕捉）→ Organize（组织）→ Distill（提炼）→ Express（表达）。
- **LLM Wiki 范式**：Raw Sources（原始）→ Wiki（AI 维护的结构化页）→ Schema（规则层立规矩）。新资料进来，AI 主动提取实体/概念、编织双链、更新索引、记录日志——知识"自动生长"。
- **关键洞见**：Obsidian = 记忆（存储 + 数据主权），AI = 思考（提炼 + 表达）；笔记超 1000 条靠人脑索引失效，必须自动化。

### 2.3 Obsidian 原生新能力（直接可用，且我们已踩在肩上）

- **Bases（数据库视图）**：从笔记 Properties/frontmatter 自动生成表格/看板/卡片视图——**正好解决"业务全景自动全面展示"**，无需全靠自建前端表格。
- Properties、双链/反链、Graph View、Local REST API（外部可读写本地库）。

> **结论**：我们要的不是"另起炉灶"，而是把已验证正确的存储底座（Obsidian vault + Markdown + frontmatter + 双链）接上"事件驱动自动汇聚 + LLM 生产侧加工 + Bases 式结构化呈现"这条被业界验证过的主线。

## 3. 优化方案设计

### 3.1 总体架构（四层）

```
┌─────────────────────────────────────────────────────────────┐
│ 采集层 Capture（事件驱动，告别人工点击）                        │
│   业务事件钩子：需求定稿/工单关闭/会议结束/运营闭环/AI报告定稿/  │
│   交付物上传  ──►  轻量调度器 APScheduler（周期补齐+增量同步）   │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 知识层 Organize + Distill（单一事实源 + LLM 生产侧加工）         │
│   pmwb_knowledge_item / link（DB 索引=真相）  ◄──►  Obsidian    │
│   文件（可读写副本）  ·  唯一路径权威源 obsidian_paths          │
│   LLM：自动摘要 / 标签 / 领域归类 / 实体抽取 / 主笔记自动区回流   │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 呈现层 Express（业务全景重做，参考 Bases）                       │
│   领域卡片网格 → 领域详情（主笔记结构化 §1-§10 + 时间线 + 关联）  │
│   顶部"产品圣经 + 时间线"横向 tab  ·  修复菜单/崩溃/主题/孤儿     │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 检索层 Retrieve（统一语义检索）                                 │
│   阶段一：DB 全文索引 + Obsidian 正文统一检索                    │
│   阶段二（可选）：向量检索 + GraphRAG 式关联推荐                 │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 核心设计原则

1. **保留 Obsidian vault 为存储底座**——数据主权、Markdown 通用、双链、可被 Bases/外部 AI 读写。
2. **DB 索引为单一事实源（SSOT）**，vault 文件是可读写副本；所有展示从 DB 聚合，不直扫文件。
3. **`obsidian_paths.py` 为唯一路径权威源**；一次性修正 `domain_code.vault_path` 与真实目录对齐（删掉虚构的"政企业务知识库"层）。
4. **事件驱动取代人工点击**；沉淀幂等（`source_type+source_id` 去重）。
5. **LLM 进生产侧**：自动摘要/标签/归类/实体抽取。

### 3.3 业务全景呈现重设计（参考 Bases，落实原设计）

- **领域卡片网格**（按 `domain_group` 分组）→ **领域详情**：主笔记结构化（§1–§10 全链路修复）+ 时间线（按月折叠，默认当月展开）+ 关联对象 Tab（需求/会议/工单/运营/交付物）。
- 顶部 **"产品圣经 + 时间线"横向 tab**（落实 memory 里已确定的设计意图）。
- 后端新增 `getDomainPanorama(domain_code)` 聚合 API，一次返回主笔记章节 + 时间线 + 关联对象，前端不再各自散取。
- 修复：统一菜单入口（停止过度 hidden）、删孤儿组件、修 3 处崩溃 API、统一浅色主题、用骨架屏替代空态堆砌。

### 3.4 自动汇聚机制（核心改造）

把现有人工 sediment 端点改为"可自动触发"，并在关键业务事件挂钩子：

| 业务事件 | 触发动作 |
|---|---|
| 需求定稿 / 关闭 | 自动沉淀 + 主笔记 §2.3/§3.2 自动区回流 |
| 开发工单关闭 | 自动沉淀到领域树 `开发交付/` |
| 会议结束 | 自动沉淀到 `会议/` |
| 运营工单闭环 | 自动沉淀到 `运营/` + 场景规则回流 |
| **AI 报告 finalize** | **自动建 `pmwb_knowledge_item` 索引**（回收 66 篇 `15-工作总结` 暗数据） |
| 操作手册上传 | 自动归档到 `05-交付物/` |
| 新增：重点工作 / 一线调研 / SQL 脚本库 / 高价值邮件 | 补全沉淀出口（取高价值片段，非全量） |

- 引入 **APScheduler**（main.py startup 注册）：周期扫描"未索引的高价值源"（如 `15-工作总结`、vault 里未索引的 .md）做增量补齐。
- **统一取数服务层**：抽出 `report_collector`/`task_center` 重复的跨表取数，供 AI 报告、知识中心、任务中心共用。

### 3.5 智能加工（LLM 生产侧）

- 沉淀时自动：`summary`（替代 `[:200]` 截断）、`tags`（替代硬编码模板）、`domain_code`（LLM 推断替代人工指定）、实体/事件抽取（喂时间线）。
- 调度器定期对 `manual/vault_sync` 旧条目补加工。

### 3.6 检索升级

- 阶段一：修复 ai_qa 不搜正文的缺口，DB 全文索引 + Obsidian 正文统一检索。
- 阶段二（可选）：向量检索（本地 pgvector / Milvus-lite）+ GraphRAG 式关联推荐。

## 3.7 领域树统筹设计（P0 硬前置，连 Obsidian 一起整治）

**目标**：让"领域分组标准（DB `domain_group`）— vault 目录结构 — 路径权威源 `obsidian_paths.py`"三者完全一致，业务知识主笔记统一在 `01-业务知识` 下。

**权威分组标准（4 类，老大确认）**：`商客业务` / `公共能力` / `系统平台` / `通用`。
- 历史 `家客业务知识库`（21 个领域）是老大旧领域，本次**不在商客主线内整治**，保留原样、暂不纳入 PMWB 知识中心索引（避免污染商客主线；后续若需接入再单独评估）。
- 错误层 `其他政企业务知识库`、`政企业务知识库` 取消，内容按业务归属归并到 4 类。

**工作核心归一（老大 2026-08-30 补充）**：当前只负责 **商客业务 + 系统平台** 两条线，其他政企业务（专线/集团短信/卫星宽带/国铁/国际）暂不负责、弱化处理；公共系统能力单独成 `公共能力` 路径。

> ### 分目录管理铁律（一级规则）
> 业务笔记、系统平台笔记、公共能力、通用 **四类分目录存放**，路径唯一、互不串门：
> | 类别 | vault 路径模板 | 示例 |
> |---|---|---|
> | 业务领域主笔记 | `01-业务知识/商客业务/{领域名}/` | 商客业务/一网通宽带/ |
> | 系统平台主笔记 | `01-业务知识/系统平台/{平台名}/` | 系统平台/政企工作台/ |
> | 公共能力主笔记 | `01-业务知识/公共能力/{能力名}/` | 公共能力/一键订购/ |
> | 通用 | `01-业务知识/通用/{...}/` | 通用/日常管理/ |
>
> **商客业务目录下不得存放系统平台主笔记**；现已混入的必须上提整合到 `系统平台/` 对应平台（见下表）。

**商客业务目录下混入的"系统平台类主笔记"整合清单（实测，P0 必修）**：

| 现状位置（商客业务下） | 整合到（系统平台下） | DB 现状/动作 |
|---|---|---|
| `商客业务/电子协议/` | `系统平台/电子协议/`（已存在主笔记，合并双份） | DB `e-contract` vault_path 误写 `政企业务知识库/业务平台/电子协议平台`，需对齐真实目录 |
| `商客业务/政企工作台/政企工作台 业务知识主笔记.md` | `系统平台/政企工作台/`（新增平台） | DB `gov-enterprise-workbench` vault_path 误写 `政企业务知识库/业务平台/政企工作台`，需对齐 |
| `商客业务/订单中心/订单商客业务中心 业务知识主笔记.md` | `系统平台/订单中心/`（新增平台） | DB `order-center` vault_path 误写 `政企业务知识库/业务平台/订单中心`，需对齐；订单中心是老大负责平台 |
| `商客业务/系统平台/系统平台 业务知识主笔记.md` | `系统平台/`（平台总览入口，归并到 `platform-group`） | DB `platform-group` 现状 vault_path=NULL，补编 |

**其他政企业务——弱化处理（不作为 P0 整治对象）**：
- `专线 / 集团短信 / 卫星宽带 / 国铁项目 / 国际业务`：DB 中 `enabled=0`、暂不负责任。保留 vault 仓库但**不纳入知识中心主线索引**，仅在"其他政企业务"归档区按需查阅；不在 P0 路径整治范围。

**公共能力——保留确认（老大单独成路径，正确）**：
- `一键订购 / 场景化销售 / 集团充值` → `01-业务知识/公共能力/{能力}/`，现状正确。
- ⚠️ 错配修正：`cj-xs 场景化销售` 的 `domain_group` 误标 `商客业务`，但 `vault_path` 已在 `公共能力/场景化销售` → 将其 `domain_group` 改为 `公共能力`。

**DB `domain_group` 归并映射（草案，已按上述规则校准）**：

## 3.8 主笔记内容结构标准化（分类型模板 + 与自动沉淀协同，P0 核心）

> **老大 2026-08-30 补充（核心）**：业务 / 系统平台 / 公共能力 三类主笔记的内容结构本应不同，但现状结构一直没定好——不单是内容缺失，连"该长什么样"都没统一。更重要的是，**主笔记结构必须和后面的"知识自动沉淀"方案协同设计**：哪些区是系统自动填充、从哪些业务事件来、什么格式，必须预先定义，否则自动沉淀无处可写、写出来也对不上。

### 3.8.2 统一设计原则

- **三类模板，各自语义**：业务 / 系统平台 / 公共能力 用**同一编号体系（§1–§N）**但章节语义按类型不同；前端按 `domain_group`（business/platform/capability）选模板。
- **三类区属性统一**：每类都分 `人工维护区(baseline)` / `自动区(auto)` / `系统维护区(system)`。**自动区绝不覆盖人工区**（沿用 `sync_main_note_from_links` 分级策略，扩展到三类）。
- **结构与自动沉淀协同**：每个"自动区"必须预先绑定**事件源 + 写入格式**，使 P1 自动汇聚能按图索骥地写；未绑定事件源的自动区在模板中标"预留"。
- **模板即权威源**：`MAIN_NOTE_SECTIONS` 改为按 `domain_group` 取三套，编号前缀与生成器/手写严格一致（修 2.1 vs 2. 的匹配 bug）。

### 3.8.5 页面化同步创建（一键新增领域+主笔记，与 §3.8 强耦合）

> **老大 2026-08-30 需求**：现在页面新增业务子领域后，还要手工去 Obsidian 对应路径下单独新建文件夹、笔记、对应模板——这步应**一键页面同步自动完成**。业务领域 + 业务笔记都应页面化管理。

**现状根因（已实证）**：
- `services/business_domain.py:424 create()` **只写 `pmwb_business_domain` 一条 DB 记录**，不碰 vault 目录、不生成主笔记、不回写 `vault_path`→ 新增后 vault 全靠人手工建，路径极易写错（现状 8 个 domain `vault_path=NULL` 即由此而来）。
- `obsidian_paths.py` 已有 `resolve_domain_path(db, code)`（按 `domain_group`+`domain_name` 算 `01-业务知识/{group}/{name}`，权威源），但**无"建目录 + 生成主笔记"函数**。
- 新建主笔记若不套 §3.8 三类模板，又回到"结构没定好"——故**同步创建必须复用 §3.8 模板**。

**目标能力（页面化知识管理后台）**：
1. **领域一键新增**：页面填 `domain_group`(4选1) + `domain_name` + `domain_code` → 后端自动：① 算 `vault_path`（`resolve_domain_path`）；② 在 vault 建目录 + 子目录（03-业务规则/05-交付物/运营/会议/开发交付）；③ 生成主笔记 `{name} 业务知识主笔记.md` 并套 **§3.8 对应类型模板骨架**（frontmatter + 人工区占位 + 自动区预留 + 系统区）；④ 回写 `vault_path` + `obsidian_path` 到 DB。页面刷新即见新领域。
2. **领域改名/改组同步**：`update` 时若 `domain_name`/`domain_group` 变更 → 重命名 vault 目录 + 主笔记文件名，回写路径（原子校验：目标不存在才重命名，避免覆盖）。
3. **业务笔记页面化**：在领域详情下支持新建子笔记/知识条目（页面填名称+类型）→ 后端在 vault 对应目录建 `.md`（带基础模板），并登记 `pmwb_knowledge_item`；不再需要开 Obsidian 手工建。
4. **双向感知**：vault 已有笔记通过 `vault_sync` 定时/手动回显到页面树（只读发现），页面是"单一管理入口"。

**后端改动清单（落地参考）**：
- `obsidian_paths.py` 新增：
  - `ensure_domain_dir(db, code) -> abs_path`：`makedirs(exist_ok=True)` 建根 + 5 个子目录，返回绝对路径。
  - `main_note_rel_path(name, group) -> str` / `build_main_note_skeleton(name, group) -> str`（按 §3.8 三套 `MAIN_NOTE_SECTIONS` 渲染 frontmatter + 章节骨架）。
- `business_domain.create/update` 增强：写 DB 后调用上述函数建 vault+主笔记；vault 不可达时记 warning、DB 仍建（不致命）。
- 新增 `create_note(db, domain_code, note_name, note_type)`（笔记页面化创建入口）。
- 前端：`BusinessDomainManage.vue` 新增表单加 `domain_group` 下拉；领域详情加"新建笔记"；提交后提示"已在 Obsidian 同步创建目录与模板主笔记"。

**安全**：建目录/重命名前校验目标不存在；主笔记已存在则不覆盖（保留人工内容）；所有写 vault 动作走 `obsidian_paths` 权威源，杜绝硬编码路径。

## 3.10 知识中心前端页面设计方案评估（不局限于「产品圣经+时间线」）

老大要求：业务全景的呈现层是知识中心给用户的最终体感，**不要被单一的「产品圣经+时间线」tab 局限**，若有更好的信息架构应评估采纳。本节对呈现层做多方案对比，结论纳入 P3。

### 3.10.1 现状呈现层痛点（已核实）
| 乱象 | 铁证 |
|---|---|
| 业务全景不是设计的 tab | `HubPanel.vue` 是固定 `.hub-split` 1fr 1fr 双栏；真正的「产品圣经+时间线」tab 只在 `DomainKnowledgeView` 弹窗里，且依赖已坏的结构化匹配 |
| 导航残缺 | 7 个子路由仅 `hub` 可见，其余 6 个全 `meta.hidden:true`（只能深链） |
| 必崩 | 3 处调不存在的 API（SearchPanel/KnowledgeView/SedimentPanel 链路） |
| 孤儿/假功能 | `SearchPanel.vue`、`SedimentPanel.vue` 零引用；`KnowledgeView.linkRequirement()` 只弹 toast 不发请求；`Math.random()` 前端生成业务主键 |
| 空态堆砌 + 硬编码深色 | 大量 `el-empty`；DB 未初始化整页空；主题硬编码深色 |

> 结论：当前呈现层**连"能进、不崩、不黑"都没做到**，谈"业务全景关联展示"为时过早——P0 必须先止血，再做方案选型。

### 3.10.2 评估维度
| 维度 | 含义 |
|---|---|
| 信息架构清晰度 | 用户能否 3 步内找到/理解知识 |
| 业务全景关联展示 | 能否「自动、全面」呈现领域全貌 **与跨领域关联**（老大的核心诉求） |
| 与四层架构契合 | 依赖知识层聚合 API（`getDomainPanorama`），不散取 |
| 开发成本/可维护 | 复用 Obsidian 原生（Bases） vs 全自建 |
| 演进性 | 是否好接 P2 智能加工 / P3 向量检索 |

### 3.10.3 候选方案对比
**方案 A：产品圣经 + 时间线（现状设计延续）**
- 结构：领域卡片网格 → 领域详情（顶部「产品圣经 / 时间线」横向 tab）。
- 业务全景 = 单领域主笔记结构化章节 + 单领域时间线。
- ✅ 贴合老大早期设计意图、落地最快；❌ 时间线只是**单域纵向事件流**，弱于「跨域关联」；全景=单域钻取，**缺全局俯视**；信息密度弱于同类知识中台门户。

**方案 B：领域驾驶舱（知识中台门户式）**
- 结构：① 总览驾驶舱（领域健康度/覆盖率/热搜词云/僵尸预警）② 领域导航（4 类分组卡片网格）③ 领域详情 Dashboard（主笔记结构化 + 关联对象 tab + 时间线 tab + 全景指标）④ 全局时间线 Feed（跨领域事件流）⑤ 统一检索。
- 业务全景 = 总览驾驶舱（全局俯视）+ 全局时间线 Feed（跨域）+ 领域详情钻取。
- ✅ 兼顾「全局俯视」与「单域钻取」，最贴合「自动全面展示」；可天然嵌知识运营看板（覆盖率/准确率/僵尸）；❌ 开发量中等，需知识层聚合 API 支撑。

**方案 C：Obsidian Bases 式统一数据库视图**
- 结构：所有知识条目（主笔记 + 业务笔记 + 沉淀记录）作为一张**可筛选数据库**，按 `domain_group`/类型/时间/标签 筛选，支持表格/看板/卡片/画廊视图切换；前端做 thin client，复用 vault Properties/frontmatter。
- 业务全景 = 筛选「某领域 + 自动区」得到的实时视图。
- ✅ 开发量最小（复用 Obsidian 原生能力）、自动全面展示天然成立（数据变→视图即变）、最契合「自动汇聚 + 自动全面展示」；❌ 强依赖 vault frontmatter 规范化（与 §3.8 模板 + frontmatter 强耦合）；章节级钻取交互需额外前端。

**方案 D：知识图谱可视化（双链/关系图）**
- 结构：领域/主笔记/业务对象为节点、关联为边，力导向图/3D 球体，点击血缘穿透、聚焦展现。
- ✅ 最直观呈现「关联」，契合 GraphRAG 关联展示、适合探索；❌ 开发成本最高（图布局/视觉降噪/交互）；当前 `pmwb_knowledge_link` 仅 115 条且稀疏、单体用户 ROI 低；**不宜做主框架**。

### 3.10.4 推荐：B + C 融合（领域驾驶舱为主框架，Bases 式视图做全景聚合）
1. **主框架 = 方案 B（领域驾驶舱）**：总分结构，全局俯视 + 单域钻取，天然承载「自动全面展示」与「知识运营看板」——直接回应老大「业务知识自动全面展示」诉求。
2. **业务全景呈现 = 方案 C 思路**：领域详情的「关联对象 / 时间线 / 自动区」用**可筛选聚合视图**（thin client 复用 vault frontmatter），不做纯手工散取表格。
3. **时间线降级为详情页一个 tab + 全局 Feed**，不再是唯一主角（修正「现状只靠时间线」的局限）。
4. **图谱（方案 D）作为 P3+ 增强**（关联探索视图），不进 P0/P1 主框架。
5. **落地前提**：依赖 §3.3 的 `getDomainPanorama` 聚合 API + §3.8 的 frontmatter 规范 + §3.9 同步创建（frontmatter 在建目录时即写入）——**呈现层与结构/沉淀层强耦合，须协同落地**。

## 3.11 各模块业务领域 / 知识关联便捷性优化评估

老大补充："其他各模块工单信息手工关联业务领域和业务知识，是否有优化方案，至少关注今后实际操作体验的便捷和好用。"——这是知识中心能被"用起来"的关键闭环：**关联这一步不爽，前面沉淀再好也白费**。本节基于代码实测（见下）给出方案，已同步落进 `prototype/knowledge-center-demo.html` 的「智能关联」与「领域管理」演示。

### 3.11.1 现状（已核实的痛点）

| 维度 | 现状（铁证） | 操作便捷性代价 |
|---|---|---|
| 字段分布 | 12 个模块有 `domain_code`（单值 String、可空、无 FK、无外键约束）；`PmwbTodo`/`PmwbWorkReport`/邮件/`SentEmail` **无字段** | 漏填无约束，事后难补 |
| 选择组件 | 统一 `BusinessDomainSelect.vue`（仅 73 行）：只二级可选、`filterable` 仅中文子串匹配、props 仅 `modelValue/disabled` | **无最近使用、无默认、无推荐、不支持拼音/编码** |
| 必填口径 | 仅需求/运营工单/会议/重点工作 4 处校验；开发工单/调研/SQL/知识中心未校验 | 口径不一，漏填后果隐蔽（领域浏览少卡片、"沉淀规则"直接报错） |
| 批量/推荐 | 全后端 grep `batch\|bulk\|批量` = **0 命中**；无智能推荐；唯一脚本 `backfill_source_domain_code.py` 仅填空、绝不覆盖 | 每条人肉点下拉，一天 10 条工单 ≈ 30+ 次冗余交互；选错只能逐条重开弹窗改 |
| 传播污染 | `domain_code` 从源工单"继承"到 knowledge_item / Obsidian frontmatter / 时间线 / 主笔记 | **源头填错 → 污染整条链路**（目录错、frontmatter 错、时间线归错域） |
| 消费盲区 | `report_collector.py` / `ai_qa.py` 中 domain 命中数 = 0 | AI 周报/AI 问答不吃领域维度，关联了也没反哺 |

### 3.11.2 优化方案（聚焦"录单即关联、好用"）

| # | 能力 | 体验收益 | 落地成本 |
|---|---|---|---|
| 1 | **智能推荐领域**（录入即关联）：表单输标题 → 实时候选（复用 `match_keywords` 关键词匹配 + 最近使用 Top3 置顶 + 拼音首字母/编码搜索），一键选中即带出 `domain_code` | 从"先想领域再找下拉"→"不用想，系统猜"，最省击 | P0 组件增强，不改表 |
| 2 | **最近使用记忆**：组件内 `localStorage`/缓存存最近选择，置顶常选项 | 连录同领域不再重复选 | P0，极低 |
| 3 | **拼音/编码搜索**：`BusinessDomainSelect` 支持 `ywt`→一网通、`ywt-broadband`→编码 | 老大批量的英文编码场景直接命中 | P0 |
| 4 | **批量关联**：列表多选 → 后端新增 `batch-set-domain` 接口，一键设领域 | 不再逐条重开弹窗；事后补填救星 | P0 加 1 接口 |
| 5 | **必填口径统一**：8 模块统一"业务类强制、其余鼓励但可批量补" | 漏填可事后批量纠，不再隐蔽 | P0 配置项 |
| 6 | **录单即沉淀**（协同 §3.8/§3.9）：保存时若该模块有自动区映射，顺带推入知识事件总线 → 自动区回流 | 关联即沉淀，关联这步顺便把知识喂饱 | P1 接事件总线 |
| 7 | **一级大类可选 + 领域模糊搜索**：组件放开一级（综合/通用之上可归大类），搜索支持模糊 | 业务不在 18 二级时不再被迫塞"综合"失真 | P0 |
| 8 | **LLM 语义推荐**（演进）：P3 把标题/内容送轻量模型推荐 Top2 领域 | 推荐更准，超长标题也能命中 | P3 |

### 3.11.3 与已有设计强耦合（呼应"协同研究"）

- **§3.8 模板**：自动区预先绑定事件源 → 能力 6「录单即沉淀」按图索骥，关联即写自动区。
- **§3.9 同步创建**：领域管理页面化 → 能力 1/2 的"领域"永远来自权威源，不出现下拉项与 vault 脱节。
- **§3.10 驾驶舱**：关联数据喂饱后，总览驾驶舱"覆盖率/僵尸/待补领域"才有意义（关联不上 = 知识盲区）。
- **消费反哺**：能力 8 + AI 周报/问答吃 domain 维度（修 `report_collector.py`/`ai_qa.py` 命中 0）→ 关联价值可见，形成正循环。

### 3.11.4 分工

- **P0（组件增强，不改数据结构）**：能力 1/2/3/4/5/7——`BusinessDomainSelect.vue` 升级 + 批量接口 + 必填统一。直接消除"手工关联太烦"。
- **P1**：能力 6 录单即沉淀（接事件总线）。
- **P3**：能力 8 LLM 语义推荐 + AI 周报/问答吃领域维度。

> DEMO 体现：`prototype/knowledge-center-demo.html` → 「智能关联」视图演示能力 1/3/4；「领域管理」视图演示 §3.9 同步创建。
