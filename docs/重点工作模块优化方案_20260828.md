# 重点工作模块优化方案（2026-08-28）

> 覆盖三个问题：① 专题工单抽屉详情加载慢；② 子页面增删改后不自动刷新；③ 在途工单「周反馈」增量更新功能。
> 状态：**待老大确认后实施**

---

## 一、现状与根因（已实测验证）

### 问题 1：抽屉弹窗加载工单详情慢

**实测数据**（本机 MySQL）：

| 接口 | 耗时 | 响应体 |
|---|---|---|
| 详情 GET /key-works/{id} | **1.495s** | 16KB（子表仅 22 条记录） |
| 列表 GET /key-works | 0.348s | 76KB（12 条主记录携带 **153 条子表记录**） |
| 基线接口（todos） | 0.242s | — |

**根因**：

1. **详情接口 8 表 joinedload 笛卡尔积**：`services/keywork.py` 的 `get()` 一次性 `joinedload` 8 张子表（goals/milestones/members/monthly_plans/weekly_plans/progresses/member_tasks/deliverables），MySQL 生成多表 LEFT JOIN，结果行数 = 各子表行数乘积，数据量再小查询也慢（实测 1.5s）。
2. **列表接口全量携带子表数据**：`KeyWorkListResponse.items` 复用 `KeyWorkOut`（含全部子表字段），relationship 均为 `lazy="selectin"`，序列化时触发 8 次子表 IN 查询 + 全量传输。列表页实际只展示主表字段，153 条子表数据纯属浪费。
3. **前端每次操作后整包刷新**：所有子表增删改成功后都调 `refreshDetail()` 全量重拉 8 个子表，连用户当前没看的 tab 也一起重载。

### 问题 2：子页面增删改后页面不自动刷新

**根因**：

1. 代码层面每次操作后**有**调用 `await refreshDetail()`，但 `refreshDetail()` 无 try/catch —— 若重拉详情失败（或慢到用户等不及），界面表现就是"操作成功提示了，但列表没变"，且无任何错误提示。
2. 全量重拉 1.5s 的体感就是"没刷新"。
3. **连带 bug**：成员待办对话框字段是 `link`，后端 schema 字段是 `link_type`/`link_id`，pydantic 静默丢弃 `link` —— 前端选"关联里程碑/月计划/周计划"实际不生效（创建本身不受影响，但关联丢失）。

### 问题 3：在途工单增量更新（新功能）

**现状**：月计划/周计划/工作进展/成员待办 4 个子页面分散在抽屉各 tab，责任人每周反馈的信息需要老大逐 tab 手动新增/编辑，无台账、无提醒、无汇总视图。

## 二、优化方案

### 方案 A：详情/列表接口性能优化（问题 1）

| # | 改动 | 说明 |
|---|---|---|
| A1 | 详情接口 `joinedload` → `selectinload` | 消除 8 表笛卡尔积，1 条主查询 + 8 条子表 IN 查询，单条详情预计 **1.5s → <100ms** |
| A2 | 列表接口瘦身 | 新建 `KeyWorkListItemOut`（仅主表字段 + 各子表 count），列表不再携带子表全量；预计列表响应 76KB → ~10KB |
| A3 | 前端抽屉打开逻辑不变 | 后端快后抽屉自然快；`refreshDetail` 仍保留（操作后兜底一致性） |

> A1 是核心，一行 option 替换即可，风险极低。

### 方案 B：子页面操作后即时刷新（问题 2）

| # | 改动 | 说明 |
|---|---|---|
| B1 | 修复 `link` → `link_type`/`link_id` 字段映射 | 关联选择真正生效 |
| B2 | 子表操作成功后**本地即时更新** | 增删改接口已返回完整记录，前端直接对 `detail.value` 对应数组 push/替换/删除（秒级可见），随后后台静默 `refreshDetail()` 兜底一致 |
| B3 | `refreshDetail` 加 try/catch + 失败提示 | 杜绝"静默失败"观感，失败弹 ElMessage.error |
| B4 | 竞态保护 | 连续操作时 serial 排队（简单 await 链即可），避免旧响应覆盖新数据 |

### 方案 C：在途工单「周反馈」增量更新功能（问题 3，核心新功能）

**设计意图**：责任人每周自助反馈 → 系统自动落进展日志 + 联动子项状态 + 形成周反馈台账。反馈内容 = 结构化三块（本周完成/下周计划/风险求助）+ 在途子项状态勾选 + 进度。

**关键前提**：PMWB 本地运行（localhost），责任人无法直接访问系统 → 「自助提交」需走**外部通道**。已调研：

| 通道 | 可行性 |
|---|---|
| 统一邮件中心 3210 | 发信 OK（nodemailer SMTP）；**收信/解析未实现**（无 IMAP 收件逻辑） |
| agent-mail 智能体邮箱（已连接） | 可收发邮件，可拉取责任人回复 |
| 内网提交链接 | 需 PMWB 绑内网 IP + 防火墙放行 + 一次性 token 鉴权，有安全成本 |
| 老大转录（兜底） | 责任人微信/口头反馈 → 老大在周反馈 tab 手动录入，保底可用 |

**C1. 新增数据表 `pmwb_key_work_weekly_feedback`**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int PK | 自增 |
| key_work_id | int FK | 所属重点工作 |
| week | varchar(10) | 周次 YYYY-Www |
| assignee | varchar(64) | 责任人 |
| source | varchar(16) | 来源：email/manual/link |
| feedback_date | date | 反馈日期 |
| done_summary | text | 本周完成 |
| next_summary | text | 下周计划 |
| risk_note | text | 风险/求助 |
| progress | int | 该责任人进度%（0-100） |
| item_updates | json/text | 子项状态更新明细（[{type: monthly/weekly/task, id, status}]） |
| status | varchar(16) | submitted（已入库）/ confirmed（老大已确认） |
| raw_text | text | 原始反馈全文（邮件原文） |
| created_at / updated_at | datetime | 时间戳 |

**C2. 后端新增接口**（挂在 /api/v1/key-works 下）

| 接口 | 说明 |
|---|---|
| `GET /key-works/{id}/weekly-feedbacks?week=` | 查某周反馈台账（含未反馈责任人清单） |
| `POST /key-works/{id}/weekly-feedbacks` | 提交一条反馈：写台账 + **自动追加 progress 进展日志**（reporter=责任人）+ 按 item_updates 批量更新月/周计划、成员待办状态 |
| `GET /key-works/{id}/weekly-feedback-form?week=` | 生成"本周反馈工作单"：聚合该工单本周责任人（月/周计划、成员待办 assignee 去重）+ 各自在途子项 |
| `GET /key-works/feedback-overview?week=` | 全部在途工单反馈总览：工单/责任人 已反馈/未反馈 徽标 |
| `POST /key-works/{id}/feedback-mails`（若走邮件通道） | 给责任人批量发送"周反馈请求"邮件（结构化格式说明） |
| `GET /key-works/feedback-inbox`（若走邮件通道） | 拉取责任人回复邮件 → 规则+LLM 解析 → 返回待确认清单（老大可改后一键入库） |

**C3. 前端新增「周反馈」页签**（工单详情抽屉内，老大确认的方案）

- 周次选择器（默认本周 `YYYY-Www`，可切历史周）
- **责任人卡片流**：每卡片 = 责任人姓名 + 状态徽标（已反馈/未反馈）+ 该责任人本周在途子项清单（每项可勾选"已完成/已延期"）
- 反馈输入：本周完成 / 下周计划 / 风险求助 三个文本框 + 进度滑块
- 「提交反馈」按钮（人工录入）；若走邮件通道：另设「发送反馈请求邮件」+「拉取邮件回复」按钮，回复解析后进待确认列表，老大确认入库
- 台账视图：切历史周可看该周全部反馈记录

**C4. 每周提醒（可选本期）**：每周五自动化任务扫描在途工单未反馈责任人，邮件/飞书提醒。

**已确认的决策**（老大拍板）：
- ✅ 责任人**自助提交**（非集中录入）
- ✅ 结构化三块（本周完成/下周计划/风险求助）+ 子项状态勾选
- ✅ 入口放**抽屉内新增 Tab**
- ✅ 与问题 1+2 **一起实施**

**待确认（唯一剩余决策）**：自助提交的主通道选哪条？
- ② **邮件回复**（推荐）：agent-mail 已连接，发"周反馈请求"邮件 + 拉取回复解析，最贴合"责任人每周反馈"场景；解析用规则分块 + Kimi LLM 兜底，老大确认后入库
- ③ **内网提交链接**：生成 token 链接发责任人，内网浏览器打开直填表单；需要 PMWB 绑内网 IP + 防火墙放行 + 轻量鉴权
- ④ **混合**：邮件为主 + 老大手动转录兜底（任何通道都能用，成本最低，推荐组合）
