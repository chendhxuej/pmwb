一、方案概览

核心目标：将用户故事自动生成策略从"按行数/人天机械拆分"升级为"合并优先 + AI 智能拆分"，严格遵循公司《用户故事拆分边界管理规范》，杜绝审计红线风险。

三种生成策略

策略标识说明状态
合并优先（rules_v2） rules_v2 检测角色/场景/闭环，同角色同场景合并为 1 条，上限 5 条 默认启用
按工作量拆分（rules_v1） rules_v1 旧版按行数/人天机械拆分，不推荐 兼容保留
Kimi 智能拆分 llm 调用 Kimi（Moonshot AI）大模型，基于公司管理规范 Prompt 生成，含合规校验 需配置 API Key

策略路由逻辑

用户点击生成
  ├─ strategy = "rules_v2"（默认）→ 规则引擎 v2 → 直接返回
  ├─ strategy = "rules_v1"        → 旧版规则 → 直接返回
  └─ strategy = "llm"             → 调用 Kimi API
                                      ├─ 成功 → 合规校验 → 返回
                                      └─ 失败 → 自动降级 rules_v2 → 返回

五、合规保障机制

1. Prompt 编码管理规范

系统 Prompt 将公司《用户故事拆分边界管理规范》全部内容编码为 LLM 指令：

  • ✅ 5 条核心拆分原则（独立业务价值 / 角色不变 / 场景隔离 / 可独立上线 / 差异显性化）
  • ✅ 4 条允许拆分判定条件（角色不同 / 场景不同 / 上线节奏不同 / 业务目标不同）
  • ✅ 4 条禁止拆分红线（按步骤拆 / 按技术拆 / 人为切分 / 强行拆分不可独立上线）
  • ✅ 输出格式模板："作为【XX操作员】，我希望【业务行为】，以便【业务价值】"
  • ✅ Few-shot 正反示例

2. 输出合规校验器

LLM 输出后经过 _validate_stories() 校验，不符合则重试或降级：

校验项规则不通过处理
角色标签每条故事必须含"作为"抛异常 → 重试
故事数量上限硬上限 5 条抛异常 → 重试
技术维度拆分检测标题禁止含"前端改造""后端接口""数据库变更"等抛异常 → 重试
空内容检测每条必须有 title + desc抛异常 → 重试

3. 降级保护

Kimi 不可用时（网络异常 / API Key 过期 / 额度用尽 / 输出不合规重试 2 次仍失败），自动降级到规则引擎 v2（合并优先策略），不会中断业务流程。

六、故障排查

问题：下拉菜单显示「Kimi（连接失败）」

排查步骤：

  1. 检查 .env 中 US_STORY_LLM_API_KEY 是否正确（当前继承自 WorkBuddy models.json）
  2. 检查 US_STORY_LLM_ENABLED=true 是否设置
  3. 访问 http://localhost:8000/api/v1/requirements/delivery/llm-status 查看 error 字段
  4. 常见错误：HTTP 401 = API Key 过期/失效；HTTP 429 = 额度用尽；超时 = 网络问题
  5. 修改 .env 后必须重启后端才能生效
问题：Kimi 生成的故事格式不对 / 内容为空

系统已内置多重 JSON 提取逻辑（兼容 Kimi 输出中文引导语、Markdown 代码块等），但仍可能遇到极端情况。解决方式：

  • 系统会自动重试 2 次
  • 2 次仍失败 → 自动降级到规则引擎 v2
  • 可查看后端日志确认具体错误：logs/ 目录
问题：需求内容太长，Kimi 报错

kimi-k2.6 上下文窗口 128K tokens，一般不会超限。但 reasoning 会消耗额外 token，如果 max_tokens 设太小可能导致内容为空。解决方式：

  • 增大 .env 中 US_STORY_LLM_MAX_TOKENS（如 8192）
  • 精简澄清内容，去掉冗余背景
  • 查看后端日志中 reasoning_tokens 占用量
