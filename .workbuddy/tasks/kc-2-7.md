# kc-2-7 业务知识主笔记体系（Domain Main Note）

> 状态：⬜待分配（S2，方案门禁待老大确认后启动）
> 依赖：kc-2-1（关联表+基础设施已合入 main@ed00cffa）
> 提出背景：kc-2-6 核查发现 kc-2-2 设计案中的「每领域一个主笔记 + 子笔记分组」模型**未实际落地**——
> `PmwbKnowledgeItem` 模型无 `note_type` 列，当前「按领域浏览」是用 `business_domain.get_related` 平铺聚合 + 关联时间线替代。
> 本任务补全设计案原定的主笔记体系。

## 1. 需求理解（待门禁确认）

**目标**：让每个二级业务领域在知识中心有唯一的「主笔记」作为领域基线入口，子笔记（需求/工单/会议沉淀）挂在主笔记下分组展示，形成清晰的领域知识层级。

**当前偏差**：
- 设计案：主笔记（note_type='main'）+ 子笔记（note_type='sub'），主笔记聚合子笔记。
- 实际：所有笔记平铺，靠 `domain_code` + `PmwbKnowledgeLink` 关联时间线聚合，无主/子区分。

**待老大确认点**：
1. 主笔记是否由系统自动为每个有笔记的二级领域生成/保活，还是手动创建？
2. 主笔记内容来源：自动汇总子笔记摘要，还是人工维护领域概述？
3. 前端「按领域浏览」页（DomainKnowledgeView）是否需要改造为主笔记+子笔记树形结构？

## 2. 方案草案

### 2.1 数据模型（backend/db/models.py）
- `PmwbKnowledgeItem` 新增列 `note_type`：枚举 `main` / `sub`（默认 `sub`），SQLite/MySQL 均加。
- 新增唯一约束或约定：每个 `domain_code` 至多一个 `note_type='main'` 笔记（可选唯一索引）。

### 2.2 迁移（alembic）
- 新建迁移：加 `note_type` 列；为已有每个有笔记的 `domain_code` 选一篇（如最早/手动指定）标记为 `main`。
- 复用 `backend/scripts/migrate_knowledge_frontmatter.py` 思路，新增主笔记 frontmatter 写回。

### 2.3 服务层（backend/services/）
- `business_domain.py`：`get_domain_main_note(domain_code)` 取主笔记；`get_related` 改为返回 `{main_note, sub_notes[]}`。
- `knowledge_link.py` / `obsidian_link.py`：主笔记沉淀时同步 `note_type` 到 Vault frontmatter。

### 2.4 前端（frontend/src/views/DomainKnowledgeView.vue）
- 领域列表点击 → 展示主笔记（概述）+ 子笔记分组（需求沉淀/工单/会议时间线）。
- 可选：主笔记编辑抽屉。

### 2.5 验收标准
- [ ] 每个有笔记的二级领域存在且仅存在一个 `note_type='main'` 笔记；
- [ ] 主笔记 frontmatter 含 `note_type: main` 且 Vault 文件一致；
- [ ] DomainKnowledgeView 按主笔记+子笔记分组展示，旧平铺视图不丢失数据；
- [ ] pytest / vite build 回归通过（零新失败）；
- [ ] 迁移脚本 dry-run + 写回无正文破坏。
