# Speckit 任务技能

## 用户输入

```text
$ARGUMENTS
```

如果用户提供了输入，你**必须**在执行前纳入考虑。

## 执行前检查

**检查扩展钩子（生成 tasks 之前）**：
- 检查 `.specify/extensions.yml` 是否存在
- 若存在，读取 `hooks.before_tasks`
- 若 YAML 无法解析，则静默跳过
- 过滤 `enabled: false`，其余默认启用
- 不要解释 `condition`
- 对每个可执行钩子，根据 `optional` 输出说明
- 若无配置则静默跳过

## 执行概要

1. **初始化**：运行 `.specify/scripts/powershell/check-prerequisites.ps1 -Json`，并解析 `FEATURE_DIR` 和 `AVAILABLE_DOCS`。所有路径都必须使用绝对路径。

2. **加载设计文档**：从 `FEATURE_DIR` 中读取：
   - **必需**：`plan.md`（技术栈、依赖、结构）、`spec.md`（用户故事及优先级）
   - **可选**：`data-model.md`（实体）、`contracts/`（接口契约）、`research.md`（决策）、`quickstart.md`（测试场景）
   - 注意：并非所有项目都会有这些文档，应基于实际存在的文档生成 tasks

3. **执行任务生成流程**：
   - 读取 `plan.md` 并提取技术栈、依赖库、项目结构
   - 读取 `spec.md` 并提取用户故事及其优先级（P1、P2、P3 等）
   - 若存在 `data-model.md`：提取实体并映射到对应用户故事
   - 若存在 `contracts/`：将接口契约映射到对应用户故事
   - 若存在 `research.md`：提取决策并转化为初始化/准备类任务
   - 按用户故事组织任务（见下方规则）
   - 生成用户故事完成顺序的依赖图
   - 为每个用户故事生成并行执行示例
   - 校验任务完整性（确保每个用户故事都具备独立可测试的必要任务）

4. **生成 `tasks.md`**：使用 `reference/tasks-template.md` 作为结构模板，并填充：
   - 来自 `plan.md` 的正确功能名
   - Phase 1：初始化/搭建任务
   - Phase 2：所有用户故事共用的基础阻塞任务
   - Phase 3+：按 `spec.md` 中优先级排列的用户故事阶段
   - 每个阶段都包含：故事目标、独立测试标准、测试任务（如果有要求）、实现任务
   - 最终阶段：收尾与横切关注点
   - 所有任务必须严格遵循清单格式（见后文规则）
   - 每条任务都要有明确文件路径
   - 依赖章节需说明用户故事完成顺序
   - 每个故事给出并行执行建议
   - 补充实现策略说明（先 MVP，再渐进交付）

5. **汇报结果**：输出生成的 `tasks.md` 路径和摘要：
   - 总任务数
   - 每个用户故事的任务数量
   - 识别出的并行机会
   - 每个故事的独立测试标准
   - 建议的 MVP 范围（通常为用户故事 1）
   - 格式校验结果：确认所有任务都符合清单格式（checkbox、ID、label、文件路径）

6. **检查扩展钩子**：在生成后检查 `.specify/extensions.yml` 中的 `hooks.after_tasks`，处理方式与前置钩子相同。

任务生成上下文：`$ARGUMENTS`

生成出的 `tasks.md` 应该是可立即执行的——每个任务都必须具体到 LLM 无需额外上下文即可执行。

## 任务生成规则

**关键要求**：任务必须按用户故事组织，以支持独立实现和独立测试。

**测试是可选的**：仅当功能规格明确要求测试，或用户明确要求采用 TDD 时，才生成测试任务。

### 清单格式（强制）

每个任务都必须严格符合以下格式：

```text
- [ ] [TaskID] [P?] [Story?] 带文件路径的任务描述
```

**格式组成**：

1. **Checkbox**：必须以 `- [ ]` 开头
2. **Task ID**：按执行顺序递增（T001、T002、T003...）
3. **[P] 标记**：仅在任务可并行执行时使用（不同文件、且不依赖未完成任务）
4. **[Story] 标签**：仅用户故事阶段任务必须携带
   - 格式：`[US1]`、`[US2]`、`[US3]` 等
   - Setup 阶段：不加故事标签
   - Foundational 阶段：不加故事标签
   - 用户故事阶段：必须有故事标签
   - Polish 阶段：不加故事标签
5. **描述**：动作清晰，并包含准确文件路径

### 任务组织方式

1. **基于用户故事（spec.md）——主组织维度**：
   - 每个用户故事（P1、P2、P3...）独立成为一个阶段
   - 将与该故事相关的模型、服务、接口/UI、测试映射到该阶段
   - 标明用户故事之间的依赖关系（多数情况应尽量独立）

2. **基于契约（contracts）**：
   - 将每份接口契约映射到其服务的用户故事
   - 若要求测试，则先在该故事阶段生成契约测试任务，再实现功能

3. **基于数据模型（data-model）**：
   - 将实体映射到需要它的用户故事
   - 若实体服务于多个故事，则放到最早的故事阶段或 Setup 阶段
   - 关系相关工作放入对应故事的服务层任务中

4. **基于基础设施与初始化**：
   - 共享基础设施 → Setup 阶段
   - 阻塞性公共前置任务 → Foundational 阶段
   - 故事专属初始化 → 放入对应故事阶段

### 阶段结构

- **Phase 1**：Setup（项目初始化）
- **Phase 2**：Foundational（所有用户故事开始前必须完成的阻塞前置）
- **Phase 3+**：按优先级排列的用户故事阶段（P1、P2、P3...）
  - 故事内部顺序：测试（如需要）→ 模型 → 服务 → 端点 → 集成
  - 每个阶段都应形成一个可独立测试的增量
- **最终阶段**：Polish & Cross-Cutting Concerns
